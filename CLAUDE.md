# CLAUDE.md — Regoro Edit

Kontext für Agenten, die in **diesem** Repo arbeiten. **Nutzung/Installation/Deployment stehen in der [README](README.md)** — hier nicht wiederholen. Diese Datei erklärt Architektur, Invarianten und wie man sicher Änderungen macht.

## Was das ist (1 Satz)
Ein einzelner Bun-Prozess, der eine **bestehende statische Website** ausliefert und auf jeder Seite unter `…/edit` einen Inline-WYSIWYG-Editor bereitstellt. Ausgegründet aus `regoro-de` (dortiges `editor/`); dieses Repo ist jetzt die Quelle der Wahrheit.

## Layout
- `src/` — Code **und** Tests (`*.test.ts`). Kern infra-agnostisch: `contract.ts` (HTML-Enumeration/Validierung), `serve.ts` (renderEditView), `apply.ts` (Edits anwenden), `git.ts` (Versionen). HTTP-/Setup-Schicht: `auth.ts`, `host.ts` (Router), `sites.ts` (Host→Website-Auflösung, Seiten-Ermittlung, Ctx-Bau), `server.ts` (startServer, beide Betriebsarten), `cli.ts` (bin, heißt installiert **`regoro`**).
- **Zwei Betriebsarten.** `regoro run <siteDir>` — ein Prozess, eine Website, `HostCtx` einmalig beim Start. `regoro serve <sitesRoot>` — ein Prozess, viele Websites, `HostCtx` **pro Anfrage** aus dem `Host`-Header (Invariante 10). Beide laufen durch denselben Router; `handleEditorRequest` weiß nichts davon.
- `src/overlay.client.js` — Browser-Overlay (Vanilla-JS-IIFE). `host.ts` importiert es als `with { type: "file" }` und liest den Pfad je Request: in dev die echte Datei (Live-Reload), im `--compile`-Binary die eingebettete Kopie. **Nicht** auf `import.meta.url` zurückbauen — im Binary zeigt das ins Leere, `/edit-assets/overlay.js` gäbe 404 und der Editor wäre stumm funktionslos. Deklaration dafür: `src/assets.d.ts`.
- `src/telefon.ts`, `src/email.ts`, `src/kennung.ts` — Normalisierung der Kontaktwege. Jeder Vergleich läuft über die **normalisierte** Form; wer das an einer Stelle vergisst, sperrt einen Kunden aus. `STANDARD_LAENDERVORWAHL` ist eine benannte Konstante, keine verstreute Annahme.
- `src/codes.ts`, `src/bremse.ts` — Einmalcodes und Versandbremse, beide **nur im Arbeitsspeicher**.
- `src/versand.ts` — SMS (seven.io) und E-Mail (Scaleway) hinter einer Schnittstelle, plus `attrappenVersand()` für Tests und lokales Ausprobieren. Konfiguration **betreiberweit** in `/etc/regoro/versand.json`, nie im Kundenordner. Ein dritter Kanal (WhatsApp) wäre eine weitere Ausprägung, kein Umbau. **Kein Test der Suite darf echt senden.**
- `src/service.ts` — reine Textgenerierung für `regoro service` (systemd-Unit + Caddy-Block), im Einzel- **und** im Sammelbetrieb (`--multi`, plus `caddyGlobalBlock()` für `on_demand_tls`). Kein Dateisystem-Zugriff; `cmdService` druckt nur. **Ändert sich `ASSET_TYPES` in `host.ts`, müssen `caddyBlock()` und beide Vorlagen mit** — `Caddyfile.example` und `Caddyfile.multi.example`. Ein Test nagelt die `@allowed`-Zeile in allen vieren aneinander fest. `ProtectHome=yes` wird weggelassen, wenn die Site unter `/home`/`/root` liegt (systemd leert das Verzeichnis sonst, der Dienst käme nicht hoch).
- **KI-Seitenleiste.** `betreiber-config.ts` (`/etc/regoro/ki.json`, **betreiberweit**), `integrationen.ts` (`.regoro/integrationen.json`, **pro Site**, Schlüssel des Kunden), `kontingent.ts`, `arbeitskopie.ts`, `validate.ts`, `relay.ts`, `recherche.ts`, `sandbox.ts`, `agent.ts`, `agent-worker.ts`, `agent-tools.ts`, `verlauf.ts` (Gesprächsverläufe: Persistenz, Auswahl, Nachlesen, Aufräumen), `modell-info.ts` (Kontextfenster beim Anbieter erfragen). Der Worker ist **dasselbe Binary** mit dem versteckten Unterbefehl `agent-worker` — kein zweites Release-Artefakt, kein Node auf dem Kundenhost.
- `scripts/gen-notices.ts` + `THIRD-PARTY-NOTICES.txt` — Lizenzhinweise, **Rechtspflicht**: Ein `--compile`-Binary trägt keine einzige Lizenzdatei aus `node_modules`, alle Lizenzen im Baum verlangen aber die Weitergabe ihrer Copyright-Hinweise. Eingebunden wie das Overlay (`with { type: "file" }`), ausgegeben von `regoro licenses`. Die Paketliste kommt aus **`bun.lock`**, nicht aus `node_modules`: 8 Plattform-Varianten von `@mariozechner/clipboard` sind hier nicht installiert, werden aber in anderen Release-Zielen ausgeliefert. Standardtexte für Pakete ohne eigene Lizenzdatei liegen in `scripts/spdx/`; fehlt dort eine benötigte Kennung, bricht der Generator ab, statt sie wegzulassen.
- `install.sh` — Installer (POSIX sh): lädt Binary + `SHA256SUMS` vom GitHub-Release, verifiziert, legt nach `~/.local/bin/regoro`. Bricht ohne `git` oder ohne Prüfsumme ab.
- `.github/workflows/release.yml` — baut auf Tag `v*` vier Binaries (`bun build --compile --target=bun-{linux,darwin}-{x64,arm64}`), erzeugt `SHA256SUMS`, hängt beides ans Release. **Asset-Namen müssen zu `install.sh` passen** (`regoro-<os>-<arch>`).
- `examples/site/` — Beispiel-Website, die die Tests als Fixture nutzen (`REAL_SITE`).

`VERSION` in `cli.ts` ist gegen `package.json` per Test festgenagelt — beide zusammen bumpen.
`cli.ts` führt `main()` nur unter `import.meta.main` aus; ohne den Guard startet ein Import die CLI.

## Nicht-verhandelbare Invarianten (bei Änderungen erhalten!)
1. **Zwei Schreibwege, zwei Regeln.** Seit der KI-Seitenleiste erzeugt nicht mehr nur der Server Markup. Die alte Invariante gilt unverändert für den Text-Editor; für den Agenten tritt eine zweite daneben. Keine der beiden ersetzt die andere.
   - **1a — Text-Editor (unverändert):** Der Client schickt **nie Markup**, nur Befehle (Text, Offsets, Format-Flags). Der Server erzeugt **jedes** `<strong>/<em>/<u>/<a>/<span style=color>/<br>`. Deshalb kein HTML-Sanitizer nötig — validiert werden ausschließlich **`href`** (`isValidHref`) und **Farbe** (`isValidColor`/`normalizeColor`). Führe keine client-gelieferten HTML-Strings ein.
   - **1b — KI-Editor (neu):** Der Agent **erzeugt** Markup, schreibt es aber nie in die ausgelieferte Website. Er schreibt in eine Arbeitskopie **außerhalb** des Site-Ordners; der Server übernimmt daraus nur Dateien, die `validateAgentOutput()` bestanden haben. Der Prüfschritt urteilt nie darüber, ob eine Änderung *gut* ist — nur über das, was kein denkbarer Kundenwunsch je erfordern würde.
     - **Inline-`<script>` ist erlaubt und wird am INHALT gemessen — wie eine eigene `.js`-Datei.** Ein pauschales Verbot stand hier einmal und kaufte nichts: Eine eigene `.js` ist erlaubt, `<script src>` ebenso, und die erzeugte CSP führt `script-src 'self' 'unsafe-inline'` mit Absicht (die Fabrik baut ihren Seitenkopf damit). Beide Formen laufen mit denselben Rechten auf derselben Herkunft; das Verbot erzwang eine Datei mehr, sonst nichts. Schlimmer: Die Asymmetrie lief falsch herum — eine neue `.js` wurde inhaltlich geprüft, ein Inline-Block gar nicht erst angesehen, sondern abgelehnt. Und es kostete real: Für eine **neue** Datei ist jeder Inline-Block zwangsläufig neu, der Agent konnte den Fabrik-Seitenkopf also nie vollständig kopieren — gemessen an einer angelegten Produktseite: Menüknopf tot, `--kanon-kopfhoehe` beim CSS-Rückfall, auf dem Handy ein zerdrückter Kopf, auf **jeder** neu angelegten Seite. Geprüft wird jetzt in beiden Formen dasselbe (Navigationsregel, Service-Worker), und zwar gegen den Vorzustand: Was schon vorher dastand, bleibt gültig. Wer das Verbot wieder einführt, muss zuerst erklären, was es gegenüber der erlaubten `.js`-Datei verhindert.
2. **Auth ausschließlich datei-basiert, Nachweis per Einmalcode:** `<siteDir>/.regoro/auth.json` (`v:2`, Listen `nummern`/`emails` + per-Site HMAC-Secret). **Kein Passwort, kein argon2id** — mit ihm verschwand ein Überlastungshebel (jeder Versuch kostete ~64 MB, ungebremst von außen auslösbar). **Fail-closed:** kein/ungültiges/veraltetes File, oder leere Kennungsliste → alle `/edit*` inkl. Anmeldung → 404. Eine `v:1`-Datei wird **abgelehnt**, nicht migriert (`pruefeAuthDatei` → `"veraltet"`).
   - **Die Anmeldung ist zweistufig:** Kennung (Telefonnummer *oder* E-Mail) → Einmalcode. Unterschieden wird an der **Anwesenheit** des Feldes `code`, nicht an seinem Inhalt und nicht an einer serverseitigen Sitzung. Auf „nicht leer" zurückgebaut hieße ein versehentlicher Leer-Klick im Code-Formular „neuen Code anfordern": eine zweite, kostenpflichtige Nachricht, und der Code aus der ersten wäre tot, weil `merkeCode` ihn ersetzt. Ein leeres Feld verbraucht auch keinen der fünf Versuche — es ist ein Vertipper, kein Rateversuch. Die Kennung reist im Formular mit; wer sie fälscht, hat trotzdem keinen gültigen Code.
   - **Dieselbe Antwort für hinterlegt und nicht hinterlegt** — in Inhalt, Statuscode **und Laufzeit**. Sonst verrät die Anmeldeseite, welche Nummern es gibt. Ebenso dürfen „Code falsch", „abgelaufen" und „Kennung unbekannt" nicht unterscheidbar sein. Tests: `login-code.test.ts`.
     - **Der Versand wird bewusst NICHT abgewartet** (`void versand.sendeCode(…).catch(…)`). Gemessen: mit `await` dauerte die Antwort 152 ms für eine hinterlegte und 0,2 ms für eine unbekannte Kennung — für jede beliebige Nummer nachprüfbar, ob sie zu dieser Website gehört. Ohne `await` bleibt ein Unterschied von ~1 µs. Nicht auf `await` zurückbauen.
     - **Ein Versandfehler geht ins Log, nie an den Browser.** Nur eine hinterlegte Kennung kann einen Versandfehler auslösen — ein 502 wäre ein rauschfreies Orakel. Der Kunde sieht auf der Code-Seite „Neuen Code anfordern".
     - **Die Frage „ist dieser Kanal eingerichtet?" steht VOR der Hinterlegt-Prüfung** und hängt nur vom gewählten Reiter ab (→ 503 für alle). Stünde sie danach, wäre der Zustand direkt nach `regoro init` — versand.json fehlt noch — ein offenes Orakel für jede Website.
   - **Codes und Bremszähler leben nur im Arbeitsspeicher** (`codes.ts`, `bremse.ts`) und gehen **niemals ins Log** — auch nicht gekürzt, auch nicht im Fehlerfall. Vergleich über `safeEqual`, nie `===`.
     - **Deshalb geht aus einer Anbieter-Antwort nur der HTTP-Status in die Fehlermeldung, nie der Rumpf** (`versand.ts` → `ruf()`). `nurCode()` **prüft** den seven.io-Statuscode gegen `^\d{3}$`, statt ihn zu kürzen — Kürzen genügte nicht: Ein Rumpf `Code: 424242` ergab `Code424242` und trug den Einmalcode vollständig ins Log (gemessen). Ein dreistelliger Wert kann keinen sechsstelligen Code enthalten. Der Rumpf gehört dem Anbieter, und eine 4xx-Antwort spiegelt gern die Anfrage zurück — die enthält Code und Empfänger. Ein Filter über Steuerzeichen genügt dafür **nicht**: der verhindert gefälschte Log-Zeilen, nicht den Code im Log. Wer die volle Antwort braucht, findet sie im Dashboard des Anbieters.
   - **Die Bremse greift VOR dem Versand** und verbucht in einem Zug mit dem Fragen. Getrennt gäbe es einen Pfad, auf dem das Verbuchen ausbleibt (Versand scheitert) — genau den würde jemand suchen, um kostenlos auszulösen. Sie zählt **auch unbekannte Kennungen**, sonst wäre sie selbst ein Orakel. Der Kostendeckel ist `MAX_PRO_KENNUNG` (nur hinterlegte Kennungen kosten Geld); `MAX_PRO_SITE` ist eine Flut-Sperre und deshalb hoch angesetzt — eine Handvoll erfundener Nummern darf nicht die Anmeldung aller Kunden einer Website sperren. Echte Flut-Abwehr gehört in den Reverse-Proxy — das gilt für **beide** Zähler.
     - **Je Kennung wächst eine Wartezeit, es gibt keinen festen Deckel** (`STUFEN_MS = [1 min, 1 min, 5 min]`, letzte Stufe gilt dauerhaft weiter). Der frühere feste Deckel („drei pro Stunde, dann zu") ist an einem echten Fall gescheitert: Drei Anfragen sind mit einem Tippfehler, einem zweiten Gerät oder einer Mail im Spam-Ordner verbraucht, und danach steht der **zahlende Kunde** 54 Minuten vor verschlossener Tür. Ein Kostendeckel, der den Kunden häufiger aussperrt als den Angreifer, ist am falschen Ende scharf. Preis der Änderung, bewusst bezahlt: höchstens ~12 Nachrichten je Stunde statt 3 — die harte Kostengrenze ist das Guthaben beim Versanddienst, nicht diese Datei.
     - **Eine erfolgreiche Anmeldung setzt die Treppe zurück** (`entsperreKennung`, gerufen direkt nach `pruefeCode(...) === "ok"`). Die Bremse begrenzt Anfragen von jemandem, der sich **nicht** anmelden kann; wer gerade einen gültigen Code vorgelegt hat, ist genau der, für den sie nie gedacht war — er darf am zweiten Gerät nicht warten. Kein Orakel: Auslösen kann es nur, wer einen gültigen Code besitzt, und beobachten nur derselbe. Die **Flut-Sperre der Website bleibt dabei unberührt** — sie zählt über alle Kennungen, und dass ein einzelner Kunde sich anmeldet, sagt darüber nichts. Beide Gegenproben stehen als Tests.
     - **Ein gezielter Lockout bleibt möglich, wird aber billiger:** Wer die Geschäftsnummer kennt (sie steht im Impressum derselben Website), hält die Codes dieses Kunden auf Abstand. Zwei Entschärfungen, beide durch Tests festgehalten: Der **zweite Kontaktweg hat einen eigenen Zähler** und bleibt offen, und die Codes des Angreifers landen **beim Kunden** und funktionieren dort. Deshalb bei jedem Kunden nach Möglichkeit Nummer **und** Adresse hinterlegen.
   - **`createAuthFile` überschreibt kommentarlos** (Kennungen **und** Secret) — deshalb guardet `cmdInit` dagegen und verlangt `--force`. Zum Pflegen der Kennungen gibt es `schreibeKennungen`/`regoro kennung`; das rührt das Secret **nicht** an, damit eine hinzugefügte Nummer keine laufende Sitzung beendet.
   - **`init`-Reihenfolge nicht umstellen:** `ensureGitignore` → `ensureRepo` → `createAuthFile`. Der Baseline-Commit entsteht, wenn `auth.json` noch **nicht existiert** — das Secret kann gar nicht hineingeraten. Und ein fehlschlagendes `git` hinterlässt keine nutzlose Auth-Datei, die der „bereits initialisiert"-Guard dann blockieren würde. Tests: `cli.test.ts` → „git schlägt fehl".
   - **Cookie-Name nie hartkodieren** — `cookieName()` benutzen. In Prod ist er `__Host-regoro_edit`; das Präfix verbietet dem Browser `Domain=`-Cookies gleichen Namens, sonst könnte bei Subdomain-Betrieb (`kunde.site.example.de`) eine Geschwister-Subdomain die Session aller anderen verdecken. Ohne `Secure` (EDITOR_INSECURE_COOKIE=1) fällt das Präfix weg, sonst verwirft der Browser das Cookie.
   - **`readCookieTokens` liest ALLE gleichnamigen Cookies**, nicht den ersten. `isAuthed` prüft jeden gegen `checkCookie`. Nicht auf „erster Treffer" zurückbauen — das ist die zweite Verteidigungslinie gegen Cookie-Tossing.
   - **Sitzungsdauer 30 Tage.** Der Normalfall soll „gar keine Nachricht" sein. Der Ausgleich: Wer sofort aussperren will, erneuert das Secret (`init --force`).
   - **Die Anmeldeseite kommt ohne JavaScript aus** — sie ist die einzige Route ohne Auth-Wall. Die Reiter sind Links (`?weg=sms|email`), kein Skript. Nicht auf JS umbauen.
3. **Nur die Website ausliefern, nichts sonst.** Zwei Schranken, beide nötig:
   - **Dotfile-Block** in `host.ts` (public-GET-Zweig + `serveStaticAsset`) → jeder Pfad mit `.`-Segment → 404. `.regoro/` ist zudem gitignored — **niemals committen**.
   - **Extension-Allowlist** `ASSET_TYPES` (`host.ts`) → alles ohne bekannte Endung → 404. Ein Site-Ordner enthält real auch Build-Artefakte (`design.json`, `images.json` mit internen Serverpfaden), Backups, Notizen. Nimm **nie** `.json`/`.yaml`/`.md` in `ASSET_TYPES` auf; `.svg` bleibt draußen (script-fähig).
   - **Der Reverse-Proxy muss dieselbe Allowlist führen.** In `Caddyfile.example` liefert Caddy die statische Site direkt aus, der Bun-Host ist dafür nicht im Pfad — ein blankes `file_server` unterläuft `ASSET_TYPES` komplett (war so, gefixt). Ändert sich `ASSET_TYPES`, ändere das Caddyfile mit. Tests dazu in `security.test.ts` („404, obwohl die Datei existiert").
4. **Routing:** Präzedenz `/edit/login` → `/edit-assets/*` → API-Routen (`save/upload/versions/restore/version`) → View-Routen (`/edit`, `/<page>.html/edit`) → public static. View unauth → **302 Login** (`?return=`, streng validiert gegen Open-Redirect). API unauth → **404**.
   - **Eine Route steht an ZWEI Stellen in `host.ts` — und die erste ist die Auth-Wand.** `isApiRoute` entscheidet, ob eine Anfrage überhaupt in den Zweig hinter dem Cookie-Test kommt; die Zuordnung `path === … → handler` steht darunter. Wer nur die zweite ergänzt, baut eine Route, die **auch angemeldet 404 gibt** — die Anfrage fällt durch bis zum statischen Ausliefern. Genau so lag `/edit/agent/verlaeufe` einen Commit lang tot da.
   - **Und der Test, der das hätte finden müssen, war grün.** `agent-routes.test.ts` prüfte „unangemeldet → 404" — das stimmte, aber aus dem falschen Grund: Eine Route, die es gar nicht gibt, antwortet ebenso. Deshalb steht dort jetzt `ERREICHBAR` neben `ROUTEN`: dieselbe Liste, einmal angemeldet gefahren, mit dem Statuscode, den sie liefern **muss**. Eine Abwesenheits-Prüfung ohne diese Gegenprobe misst nichts. Wer eine Route ergänzt, ergänzt beide Listen.
   - **Der Proxy-Matcher muss `isEditorPath()` spiegeln.** `path /edit*` reicht **nicht**: es verfehlt die Suffix-Route `/<page>.html/edit` (der Editor war in Prod für jede Unterseite 404) und fängt zugleich öffentliche Seiten wie `/edit-preise.html` ein. Korrekt: `path /edit /edit/* /edit-assets/* */edit`. Gilt für `Caddyfile.example` **und** `caddyBlock()` in `service.ts` — beide gemeinsam ändern.
5. **Symlink-sicheres Schreiben:** `pathInsideSite()` (realpath-Containment, fail-closed) vor jedem Write in `handleUpload`/`handleSave`/`handleRestore`. Nicht entfernen.
6. **Range-Format-Ops werden beim Speichern aus dem Live-DOM abgeleitet** (`collectRangeOpsFromDom` in overlay.client.js) — additive Formatierung über `.__regoro-range-fmt`-Spans, Entfernung über `.__regoro-range-unfmt`-Marker. Grund: robust gegen zwischenzeitliche Textedits. Nicht auf fixe gespeicherte Offsets zurückbauen.
7. **Ephemer:** `data-edit-idx`/`data-edit-img-idx`/`data-edit-del-idx`/`data-edit-br-idx` werden nur in der `/edit`-Response injiziert, **nie auf Platte**. Roh-HTML ist die einzige Quelle, bei jedem `/edit`-Load neu abgeleitet.
8. **Optimistic Locking:** `fileHash` → Mismatch = 409. Versionen = Git **pro Site** (`repoRoot === siteDir`); `init` legt einen pristine Baseline-Commit an.
   - **`restoreVersion` stellt GENAU EINEN Pfad wieder her und löscht nie etwas** (`git checkout <commit> -- <pagePath>`). Vom Agenten *hinzugefügte* Dateien überleben damit jede Wiederherstellung. Der Editor hat überhaupt keinen Weg, eine Datei zu entfernen, und keinen, einen ganzen Lauf zurückzunehmen — die Versionsliste arbeitet **pro Seite**, nicht pro Lauf. Der Plan-Satz „die Versionsliste ist das Sicherheitsnetz" gilt mit dieser Einschränkung.
   - **Folgenlos für tote Dateien, gefährlich für alles, was sich selbst am Leben hält.** Eine zurückgebliebene Datei ist nach der Wiederherstellung nirgends mehr eingebunden und damit wirkungslos. Ein **Service Worker** ist die Ausnahme: Der Browser hält seine Registrierung, er überlebt die Wiederherstellung und liefert dem Besucher weiter die entstellte Seite, während `curl` die saubere ausliefert — nachgewiesen. Deshalb lehnt der Validator `navigator.serviceWorker` ab. Wer künftig etwas zulässt, das sich **selbst am Leben hält** (Service Worker, `registerProtocolHandler`, persistente Storage-Registrierungen), muss zuerst diese Eigenschaft ändern — nicht die Regel lockern.
9. **Das Site-Repo ist die einzige Quelle der Kundenänderungen.** Der Editor schreibt direkt in die ausgelieferten Dateien; die Website-Pipeline kennt diese Commits nicht. Kein Befehl darf `.git` löschen, solange mehr als der Baseline-Commit darin steht — `cmdDisable` prüft das über `countCommits()` und bricht bei `--purge` ab. `disable` ohne `--purge` entfernt nur `.regoro/` (Editor aus, fail-closed) und lässt Website wie Historie unberührt.
10. **Kundentrennung im Sammelbetrieb:** `HostCtx` entsteht pro Anfrage aus dem normalisierten `Host`-Header. Die Trennung zwischen Kunden ruht auf drei unabhängigen Stützen: der Host-Auflösung (`sites.ts`, fail-closed), dem site-eigenen HMAC-Secret in `auth.json` (ein fremdes Cookie ist nicht verifizierbar) und `resolvePage`/`pathInsideSite` (ein fremder Pfad ist nicht auflösbar). Keine der drei darf entfallen — die erste ist Zuordnung, die zweite Identität, die dritte Containment. Tests: `multisite.test.ts`.
   - **Stütze 2 hält nur, solange die Geheimnisse verschieden sind.** Wird ein Site-Ordner samt `.regoro/` kopiert, teilen sich zwei Kunden Secret **und** Passwort-Hash — dann gilt nicht nur das Cookie des einen beim anderen, sondern dasselbe Passwort öffnet beide Logins (ein an den Host gebundenes Cookie schlösse nur die erste Hälfte). `erstelleSecretWache()` in `sites.ts` erkennt das und liefert für **beide** Seiten `auth === null` (Editor 404, Website läuft weiter). Zugeordnet wird über den **Ordner** (realpath), nicht den Hostnamen — zwei Namen per Symlink auf dasselbe Verzeichnis sind ein legitimer Alias. Nicht entfernen.
   - **Die Wache leitet aus dem IST-Zustand ab, nicht aus der Geschichte** — sie sieht das Sammelverzeichnis reihum durch (höchstens einmal pro `SECRET_SCAN_TTL_MS`), statt gesehene Geheimnisse zu sammeln. Nicht auf ein Gedächtnis zurückbauen: das hätte zwei gemessene Löcher — zwei gleichzeitig angelegte Duplikate fielen nie auf, wenn nur eines je eine Editor-Anfrage bekommt, und eine behobene Kollision heilte erst beim Neustart, was den unbeteiligten Kunden aussperrt. Die Deckelung per TTL ist Notwehr: `/edit/login` ist unauthentifiziert, eine Durchsicht pro Anfrage wäre ein Verstärker (eine Anfrage → N Dateizugriffe).
   - **`normalizeHost` ist zugleich der Traversal-Schutz** — der Host-Header wird zum Pfadsegment. Nicht lockern; `resolveSite` prüft zusätzlich auf *direktes* Kind des Sammelverzeichnisses.
   - **Einen Kill-Switch braucht der Sammelbetrieb nicht:** `buildCtx` liest `auth.json` pro Anfrage, `regoro disable` wirkt dadurch von selbst sofort. Im Einzelbetrieb bleibt der Guard in `server.ts`.
   - **Im Caddy-Block des Sammelbetriebs steht der Host-Header im `root`-Pfad** (`root * <sitesRoot>/{host}`). Deshalb sitzt `@badhost` (Zeichensatz `CADDY_HOST_RE`) davor: gemessen liefert `Host: ..` sonst Dateien **eine Ebene über** dem Sammelverzeichnis mit 200 aus. Go weist `/` im Host selbst ab (400), reine Punkte nicht.
   - **Caddys `{host}` ist der Host-Header wörtlich** — es normalisiert nichts. Deshalb spiegelt `CADDY_HOST_RE` die `HOST_RE`-Grammatik aus `sites.ts` Zeichen für Zeichen (nur Kleinbuchstaben, echte Label), per Test aneinander gebunden. Eine laxere Fassung ließ `a..b` und `KUNDE.DE` durch: Caddy lieferte den gleichnamigen Ordner öffentlich aus, während der Editor denselben Host ablehnte — ein Publikationsweg, den kein Editor-Werkzeug zeigt. Caddy darf **strenger** sein als der Editor, nie laxer. **Site-Ordner immer kleingeschrieben und ohne `www.` anlegen.**
   - **`on_demand_tls` ohne `ask` ist grob fahrlässig** — jeder fremde Hostname könnte Zertifikatsanfragen auslösen. `TLS_ASK_PATH` (`server.ts`) antwortet nur für existierende Ordner; der Pfad ist per Test an `caddyGlobalBlock()` gebunden.
11. **Der Agentenprozess hält keine Zugangsschlüssel und besitzt kein Werkzeug für beliebige Netzverbindungen.** Suche, Seitenabruf und Modellaufruf laufen über den **Elternprozess**; der Schlüssel wird erst in der Loopback-Weiterleitung (`relay.ts`) angehängt. Der Grund ist die Kombination, die 2025 reihenweise ausgenutzt wurde (Cursor CVE-2025-54135, Copilot CVE-2025-53773, GitLab Duo): fremder Text als Eingabe, ein Geheimnis in der Umgebung, ein offener Ausgang. Zwei davon nehmen wir dem Agenten weg.
    - **Was der Worker über die Außenwelt wissen muss, erfragt der ELTERNPROZESS und reicht es durch.** Der Worker läuft mit `allowModelNetwork: false` und registriert sein Modell selbst — er kann pi gar nicht beim Anbieter nachfragen lassen. Die Versuchung ist dann, die Angaben fest einzutragen, und genau das war passiert: `contextWindow: 128_000` stand im Code, während OpenRouter für dasselbe Modell 1.048.576 meldet (`top_provider.context_length`; alle 424 Modelle führen den Wert). Folge, gerechnet: pi verdichtete ab 111.616 Token statt ab 1.032.192 — mitten in großen Aufträgen (größter gemessener Lauf: 207.371 Token), jede Verdichtung ein zusätzlicher abrechenbarer Modellaufruf, und `keepRecentTokens` (20.000) warf dabei fast das ganze Gespräch weg. `modell-info.ts` fragt jetzt im Elternprozess einmal je Modell nach (gecacht, 4 s Zeitlimit, **fail-soft** auf den alten Wert) und gibt das Ergebnis als `REGORO_CONTEXT_WINDOW` und `REGORO_MAX_TOKENS` mit. Die Sandbox bleibt unberührt. **Wer hier eine weitere Anbieterangabe braucht, geht denselben Weg — nicht die Zahl in den Worker schreiben.**
      - **`top_provider.context_length` schlägt `context_length`.** Das erste ist, was der tatsächlich bedienende Anbieter kann, das zweite das theoretische Maximum des Modells; bei `glm-5.3-flash` sind das 1.048.576 gegen 1.310.720. Die größere Zahl anzunehmen hieße, Anfragen zu bauen, die abgelehnt werden.
      - **Der Ausgabedeckel (`maxTokens`) hing an derselben Krankheit** und war 16.384 — auf der Leitung nachgemessen geht er als `max_completion_tokens` wirklich an den Anbieter. Zu knapp an zwei Stellen zugleich: Werkzeug-Argumente sind Ausgabe (`write_file` übergibt die ganze Datei, 16.384 Token sind grob 55–60 KB HTML), und pi stutzt das Denk-Budget auf denselben Deckel zurecht. Jetzt `min(150.000, was der Anbieter meldet)`, ohne dessen Angabe gedeckelt durch das Kontextfenster — die einzige Schranke, die sich aus dem Modell selbst ergibt. Gemessen: OpenRouter nimmt einen zu großen Wert stillschweigend an und klemmt intern; ein strenger OpenAI-kompatibler Server lehnt ab. Auf keines von beiden verlassen wir uns.
      - **Die Abfrage ist eine Stellschraube, keine Voraussetzung.** Kein Anbieter, kein `/models`, kaputtes JSON, Zeitlimit — alles fällt auf den Vorgabewert zurück und der Lauf startet. Auch der Rückfall wird gemerkt, sonst wartete jeder Lauf eines Anbieters ohne `/models` erneut ins Zeitlimit.
    - **Der Worker startet aus einer Allowlist-Umgebung**, nicht aus `process.env` minus ein paar Namen. Auf der Entwicklungsmaschine sind `HTTP_PROXY`/`HTTPS_PROXY` gesetzt; erbte der Worker sie, gelänge ein Modellaufruf **am Relay vorbei** — und ein kaputtes Relay fiele niemandem auf.
    - **Drei Grenzen, keine ersetzt die andere:** Betriebssystem (`bwrap` je Lauf + systemd `ProtectSystem=strict`), Werkzeuge (eigene, kein `bash`, kein generisches Netzwerkzeug), Browser (CSP im Caddy-Block). Die dritte liegt außerhalb dessen, was der Agent schreiben kann — deshalb steht sie im Proxy und nicht im HTML.
    - **`regoro ki` ist betreiberweit** (`/etc/regoro/ki.json`), wie `versand.json`. `regoro disable` schaltet **einen** Kunden ab und lässt sie unangetastet — sonst nähme das Abschalten eines Kunden allen anderen die KI. Die Kundenschlüssel liegen getrennt davon pro Site in `.regoro/integrationen.json`.
    - **Zwei Eigenheiten von `bwrap` unter `--ro-bind / /`**, beide in `sandbox.ts` gelöst und beide dieselbe Familie wie die `ProtectHome`-Falle:
      - **Ein Deckel auf einen Pfad, den es auf dem Host nicht gibt, bricht den Lauf ab** — gemessen: `bwrap: Can't mkdir /etc/gibt-es-nicht: Read-only file system`. Im nur lesbaren Wurzeldateisystem lässt sich kein Einhängepunkt anlegen. Deshalb wirft `sandboxArgv` nicht existierende Ziele vorher raus. **Die Kehrseite: Ein fehlendes Verzeichnis wird stillschweigend NICHT zugedeckt.** Für `/etc/regoro` ist das folgenlos, solange es leer ist — die Deckelliste entsteht bei jedem Lauf neu, ein später angelegter Schlüssel ist ab dem nächsten Lauf verdeckt. Wer den Filter entfernt, bekommt statt dessen abgebrochene Läufe auf jedem Host ohne `/etc/regoro`.
      - **`--tmpfs /home` verdeckt auch das Binary**, wenn es dort liegt (`bwrap: execvp: No such file or directory`). Deshalb holt `sandboxArgv` die Programmdatei mit `--ro-bind` hinter dem Deckel zurück — nur die Datei, nicht ihr Verzeichnis. In Produktion liegt das Binary in `/usr/local/bin` und der Fall tritt nie ein; er trifft ausschließlich die Entwicklungsmaschine und verführt dort zur bequemen Abhilfe, den `/home`-Deckel wegzulassen.
    - **Zwei systemd-Schalter brechen `bwrap` lautlos** und fehlen in `systemdUnit()` mit Absicht: `RestrictNamespaces=yes` (sperrt alle Namespace-Typen; bwrap braucht `user`, `mnt`, `pid`) und `SystemCallFilter=@system-service` (schließt `@mount` aus — nachgezählt mit `systemd-analyze syscall-filter`). Nicht „als Hardening nachtragen".
    - **`LoadCredential=` braucht `SetCredential=ki:{}` daneben.** Gemessen auf systemd 255: Fehlt `/etc/regoro/ki.json`, bricht `LoadCredential` den Start mit `status=243` ab — der Dienst läuft nicht mehr. Mit dem Fallback startet er, `loadKiConfig` gibt für `{}` null zurück, die KI ist aus. Fail-closed statt tot.
    - **`WorkingDirectory=` darf NICHT gequotet werden** (`sdPfad()`, nicht `sdQuote()`). systemd nimmt dort den Rest der Zeile wörtlich, die Anführungszeichen würden Teil des Pfades: „path is not absolute", der Dienst startet nicht. Für `ExecStart=` und `ReadWritePaths=` sind sie umgekehrt zwingend. Beides gemessen.

## Testen / Checks
```bash
export PATH="$HOME/.bun/bin:$PATH"
bun x tsc --noEmit       # ZUERST. Typecheck (tsconfig include: src/**/*.ts)
bun test                 # ~1490 Tests (Fixtures kopieren examples/site in tmp-Dirs)
bun build src/overlay.client.js --target=browser >/dev/null   # Syntax-Check des Client-JS (tsc erfasst es NICHT)
caddy validate --config Caddyfile.example --adapter caddyfile        # Proxy-Vorlage Einzelbetrieb
caddy validate --config Caddyfile.multi.example --adapter caddyfile  # Proxy-Vorlage Sammelbetrieb
bun scripts/gen-notices.ts --check   # Lizenzhinweise aktuell? (roter Release-Build sonst)
bun build --compile src/cli.ts --outfile /tmp/regoro           # Binary — bricht bei Asset-Fehlern NICHT, erst zur Laufzeit
```
- **`tsc` vor `bun test`, immer.** `bun test` **führt TypeScript aus, ohne es zu prüfen** — ein Typfehler ist für die Suite unsichtbar. Genau deshalb konnte `src/cli.ts` über mehrere Commits unübersetzbar sein, während alle Tests grün meldeten (das fehlende `firecrawlKey` im Objektliteral). Umgekehrt sind Testfehler nach einem gescheiterten Typecheck fast immer Folgefehler und kosten nur Lesezeit.
- **Ein Nachweis, der nicht anschlagen kann, beweist durch sein Ausbleiben nichts.** An einem Tag dreimal dieselbe Fehlerklasse, jedes Mal an anderer Stelle und von jemand anderem gefunden:
  - `test.skipIf` wertet beim **Einsammeln** aus, vor jedem `beforeAll` — vier Binary-Tests waren dauerhaft übersprungen und meldeten **grün**.
  - Zwei `service.test.ts`-Zusicherungen nagelten die **kaputte** Form von `WorkingDirectory=` fest; deshalb erzeugte der dokumentierte Deploy-Weg nie eine startfähige Unit, und niemand sah es.
  - Die Prüfung „Agent-Routen geben 404 ohne `ki.json`" lief zuerst **unangemeldet** — dort geben sie ohnehin 404 (Invariante 4). Das erwartete Ergebnis kam aus dem falschen Grund.

  Zeichenketten-Prüfungen halten fest, was wir für richtig **halten**; ein Vergleich mit der eigenen Erwartung kann einen Irrtum in der Erwartung grundsätzlich nicht finden. **Wo ein Test eine Abwesenheit behauptet** („kein fatal error", „kein Proxy-Durchgriff", „keine Datei außerhalb"), gehört deshalb eine Gegenprobe daneben, die den Messapparat selbst prüft. Die drei, die dafür im Repo stehen: das absichtlich wieder eingebaute Quoting, das `systemd-analyze` als `fatal error` sehen **muss**; das Kind mit geerbter Umgebung, das durch den Attrappen-Proxy **durchkommen muss**, bevor gezeigt wird, dass der echte Lauf scheitert; und die Attrappe, die meldet, dass sie den Ausbruch **wirklich versucht** hat und an EROFS gescheitert ist — ohne sie wäre der wichtigste Test dieser Arbeit auch dann grün, wenn sie gar nichts täte.

  Und wo es geht: **das echte Werkzeug fragen**, statt die erzeugte Zeichenkette zu vergleichen — `systemd-analyze verify`, echtes `caddy` auf der Leitung, kompiliertes Binary ohne `bun` im PATH. Genau diese drei Prüfungen haben die drei teuersten Fehler gefunden.
- **Das Binary muss nach jeder Änderung an Asset-Laden/Pfaden echt geprüft werden**, `bun test` deckt nur den dev-Pfad ab. Minimal: Binary bauen, `PATH=/usr/bin:/bin` (kein bun), `regoro init` + `run` auf einer tmp-Kopie (Port über `PORT=…`, **`run` kennt kein `--port`**), dann `/edit-assets/overlay.js` → muss 200 liefern und **deutlich über 50 KB** sein, nicht 404. Bewusst eine Schwelle statt eines Punktwerts: Die Datei wächst mit jedem Ausbau (91 KB → 116 → 132 innerhalb eines Tages), und ein Punktwert wird bei jedem Wachstum zum falschen Alarm. Geprüft wird „ausgeliefert und nicht leer", nicht „exakt so groß". Dasselbe für die Lizenzdatei: `regoro licenses | wc -c` muss ~620.000 liefern, nicht 0. Das Binary ist ~90 MB.
- **Die erzeugte systemd-Unit gegen echtes systemd prüfen**, nicht nur per String-Vergleich: `regoro service <site> --systemd > /tmp/x.service && systemd-analyze verify /tmp/x.service`. Ein Textvergleich hat jahrelang eine Unit durchgewinkt, die wegen des gequoteten `WorkingDirectory=` gar nicht startete. `systemd-run --user -p …` prüft einzelne Direktiven ohne root.
- **Der SSE-Strom hängt nicht an Caddy, sondern am ersten Byte.** Gemessen (caddy 2.11.4): Caddy gibt die Antwort-Header erst mit dem ersten Körper-Byte heraus — 4,00 s Verzögerung, wenn der Lauf 4 s schweigt, und `flush_interval -1` ändert daran **nichts**. Deshalb schickt der Editor beim Verbinden sofort einen SSE-Kommentar (`: verbunden`); damit sind es 0,002 s. Nicht entfernen, und die Verzögerung nicht im Proxy suchen.
- **install.sh ist ungetestet durch die Suite.** Prüfen gegen einen lokalen „Release": Binary + `sha256sum regoro-* > SHA256SUMS` in einen Ordner, `python3 -m http.server`, dann `HOME=/tmp/x REGORO_BASE_URL=http://localhost:PORT sh install.sh`. Auch die Abbruchpfade fahren (manipuliertes Binary → Prüfsummen-Fehler, fehlendes SHA256SUMS, fehlendes git).
- **overlay.client.js ist von keiner Prüfung erfasst** — `tsc` sieht sie nicht an (kein TypeScript), und `bun build --target=browser` prüft nur, ob sie sich parsen lässt. Ob die Oberfläche das Richtige **anzeigt**, steht damit nirgends fest, und genau dort kamen zwei echte Fehler heraus (ein misslungener Lauf sah aus wie ein Erfolg; ein nachgereichter Lauf wäre nie angezeigt worden).
  - **Für die KI-Seitenleiste gibt es dafür `scripts/seitenleiste-pruefstand.ts`** (`bun scripts/seitenleiste-pruefstand.ts`, Port 8794). Er liefert die **echte** `overlay.client.js` mit erfundenen Ereignisfolgen aus — kein Modell, kein Kontingent, keine Sandbox, kein Netz, immer dasselbe Ergebnis — und druckt je Fall die Erwartung im Klartext plus einen fertigen headless-Aufruf. **Erst dort nachsehen, bevor jemand so etwas neu baut.** Bewusst ein Werkzeug und keine `*.test.ts`: Der Browser-Treiber liegt außerhalb des Repos, und ein Test, der überall außer auf einer Maschine übersprungen wird, sieht wie Abdeckung aus und ist keine.
  - **Der Prüfstand deckt inzwischen zwölf Fälle ab**, davon fünf für die Gesprächsliste (`verlauf-nachlesen`, `-blaettern`, `-waehlen`, `-liste`, `-fehlt`). Er lässt sich vollständig maschinell fahren: Er druckt je Fall den headless-Aufruf samt Sollwert, ein Treiberskript vergleicht beides. Die Erwartung steht dabei **nur** im Prüfstand — ein Treiber mit eigener Erwartungsliste wäre eine zweite Wahrheit.
  - **Der Fall `verlauf-fehlt` ist kein Randfall, sondern die Zusicherung**, dass ein Server ohne die Verlaufsrouten (404) die Leiste nicht lahmlegt. Die Gesprächsliste ist Komfort; sie darf nie im Auftragsweg stehen.
  - **Zwei Fallen im Prüfstand selbst, beide dort hineingelaufen** — er ist Code und irrt wie jeder andere: `Number(null)` ist **0**, nicht `NaN`, also lieferte die erste Seite eines Gesprächs (ohne `vor`) `slice(0,0)` und damit nichts; und „welche Fälle sind Nachlese" stand als `fallName === "…"` fest im Server statt am Fall. Beide Male sah es nach einem Fehler im Overlay aus, und beide Male war der Messapparat schuld. Wenn ein neuer Fall leer bleibt: erst den Prüfstand verdächtigen.
  - **Der Prüffall steckt im Cookie, nicht im Pfad.** Das Overlay ruft seine API unter festen absoluten Pfaden auf (`/edit/agent/...`); von einem Pfad-Präfix wäre dort nichts übrig, und jeder Fall zeigte dasselbe. Wer das übersieht, sucht den Fehler im Overlay statt im Prüfstand.
  - **Die Client-Datei bei JEDER Anfrage frisch von Platte lesen**, nie beim Start einmal. Sonst prüft man einen alten Stand und hält eine Änderung für wirkungslos. `host.ts` macht es aus demselben Grund so.
  - Für den **Text-Editor** (Selektion, Formatierung, Speichern) gibt es keinen Prüfstand: init+run auf einer temp-Kopie, im headless-Browser skripten, gespeichertes HTML prüfen.
- **Die Caddyfile-Vorlagen sind inzwischen weitgehend getestet.** `csp.test.ts` fährt ein echtes caddy hoch und prüft den ausgelieferten Header auf der Leitung — dass die CSP auf statischen Seiten steht und auf `/edit*` **nicht**, dass `design.json` und verschachtelte Dotfiles 404 geben, und dass eine freigeschaltete Browser-Herkunft wirklich im Header ankommt. Die `@allowed`- und die CSP-Zeile sind zusätzlich in Generator und **beiden** Vorlagen aneinander gepinnt.
  **Ungetestet bleibt der `on_demand_tls`-Pfad des Sammelbetriebs** — der braucht ACME und gehört in die Handprüfung. Zum Prüfen lokal nachbauen: Domain → `:PORT`, `auto_https off`, `reverse_proxy` → `respond`, dann per curl gegen einen Ordner mit Fremd-Datei (`design.json`, `dump.sql`) fahren — die müssen 404 geben, `/`, `*.html`, `*.css`, Unterordner-Assets weiterhin 200. **Auch verschachtelte Dotfiles testen** (`/assets/.private.html`, `/a/.hidden/notes.txt`): Caddys `path`-Matcher ist Glob, kein Segment-Matcher — `path /.*` deckt nur führende Punkte, daher `path_regexp (^|/)\.`.

## Fallstricke
- **Server nicht mit `repoRoot` = diesem Repo starten** für Dogfooding: der Save committet dann in genau dieses Repo. Immer auf einen **separaten Site-Ordner** zeigen (`cli.ts <site>` setzt `repoRoot = siteDir`).
- `EDITOR_INSECURE_COOKIE=1` (Cookie ohne `Secure`) wird **nicht** für `http://localhost` gebraucht — Browser akzeptieren dort `Secure`/`__Host-`-Cookies (in Chromium verifiziert), und **`curl` ebenfalls** (8.5 nachgemessen: Anmeldung über Loopback, danach `/edit` → 200 mit Jar, 302 ohne). Nötig nur bei HTTP unter fremdem Hostnamen/LAN-IP; dort verwirft der Browser das Cookie sonst **stumm** (Login-Schleife ohne Fehlermeldung). `insecureOriginWarning()` in `host.ts` warnt auf der Login-Seite vor. Nie in Prod.
  - **Der Schalter verfälscht die Prüfung, nicht nur die Sicherheit:** Ohne `Secure` fällt auch das **`__Host-`-Präfix** weg (`cookieName()`), denn der Browser verwürfe das Cookie sonst. Ein Durchlauf mit dem Schalter prüft also **nicht** den Produktions-Cookie — die Schutzwirkung des Präfixes gegen Cookie-Tossing bleibt ungetestet. Beim Ausprobieren deshalb weglassen, wo er nicht nötig ist.
  - **Eine leere Cookie-Datei ist meist ein Messfehler.** `curl` schreibt HttpOnly-Cookies mit `#HttpOnly_` am Zeilenanfang; ein `grep -v '^#'` filtert sie weg, und die Datei sieht leer aus, obwohl das Cookie darin steht. Genau daran ist eine Handprüfung schon einmal gescheitert und hat fälschlich `EDITOR_INSECURE_COOKIE=1` nachgezogen. Prüfen lässt es sich stattdessen am Verhalten: mit Jar 200 auf `/edit`, ohne Jar 302.
- Beim Ausprobieren `examples/site` nicht direkt bespielen (sonst nested `.git`/`.regoro` im Repo) — auf eine Kopie in `/tmp` arbeiten.
- Änderungen werden **nicht** automatisch mit dem alten `regoro-de/editor/` synchronisiert — dieses Repo pflegen.
