# CLAUDE.md — Regoro Edit

Kontext für Agenten, die in **diesem** Repo arbeiten. **Nutzung/Installation/Deployment stehen in der [README](README.md)** — hier nicht wiederholen. Diese Datei erklärt Architektur, Invarianten und wie man sicher Änderungen macht.

## Was das ist (1 Satz)
Ein einzelner Bun-Prozess, der eine **bestehende statische Website** ausliefert und auf jeder Seite unter `…/edit` einen Inline-WYSIWYG-Editor bereitstellt. Ausgegründet aus `regoro-de` (dortiges `editor/`); dieses Repo ist jetzt die Quelle der Wahrheit.

## Layout
- `src/` — Code **und** Tests (`*.test.ts`). Kern infra-agnostisch: `contract.ts` (HTML-Enumeration/Validierung), `serve.ts` (renderEditView), `apply.ts` (Edits anwenden), `git.ts` (Versionen). HTTP-/Setup-Schicht: `auth.ts`, `host.ts` (Router), `sites.ts` (Host→Website-Auflösung, Seiten-Ermittlung, Ctx-Bau), `server.ts` (startServer, beide Betriebsarten), `cli.ts` (bin, heißt installiert **`regoro`**).
- **Zwei Betriebsarten.** `regoro run <siteDir>` — ein Prozess, eine Website, `HostCtx` einmalig beim Start. `regoro serve <sitesRoot>` — ein Prozess, viele Websites, `HostCtx` **pro Anfrage** aus dem `Host`-Header (Invariante 10). Beide laufen durch denselben Router; `handleEditorRequest` weiß nichts davon.
- `src/overlay.client.js` — Browser-Overlay (Vanilla-JS-IIFE). `host.ts` importiert es als `with { type: "file" }` und liest den Pfad je Request: in dev die echte Datei (Live-Reload), im `--compile`-Binary die eingebettete Kopie. **Nicht** auf `import.meta.url` zurückbauen — im Binary zeigt das ins Leere, `/edit-assets/overlay.js` gäbe 404 und der Editor wäre stumm funktionslos. Deklaration dafür: `src/assets.d.ts`.
- `src/telefon.ts`, `src/email.ts`, `src/kennung.ts` — Normalisierung der Kontaktwege. Jeder Vergleich läuft über die **normalisierte** Form; wer das an einer Stelle vergisst, sperrt einen Kunden aus. `STANDARD_LAENDERVORWAHL` ist eine benannte Konstante, keine verstreute Annahme.
- `src/codes.ts`, `src/bremse.ts` — Einmalcodes und Versandbremse, beide **nur im Arbeitsspeicher**.
- `src/versand.ts` — SMS (seven.io) und E-Mail (Scaleway) hinter einer Schnittstelle, plus `attrappenVersand()` für Tests und lokales Ausprobieren. Konfiguration **betreiberweit** in `/etc/regoro/versand.json`, nie im Kundenordner. Ein dritter Kanal (WhatsApp) wäre eine weitere Ausprägung, kein Umbau. **Kein Test der Suite darf echt senden.**
- `src/service.ts` — reine Textgenerierung für `regoro service` (systemd-Unit + Caddy-Block), im Einzel- **und** im Sammelbetrieb (`--multi`, plus `caddyGlobalBlock()` für `on_demand_tls`). Kein Dateisystem-Zugriff; `cmdService` druckt nur. **Ändert sich `ASSET_TYPES` in `host.ts`, müssen `caddyBlock()` und beide Vorlagen mit** — `Caddyfile.example` und `Caddyfile.multi.example`. Ein Test nagelt die `@allowed`-Zeile in allen vieren aneinander fest. `ProtectHome=yes` wird weggelassen, wenn die Site unter `/home`/`/root` liegt (systemd leert das Verzeichnis sonst, der Dienst käme nicht hoch).
- **Die drei Zustände.** `entwurf.ts` (Entwurfs-Repo anlegen und finden, `istNichtMigriert`), `veroeffentlichen.ts` (Abgleich Entwurf → Site-Ordner, Prüfsummen-Notbremse), plus die `schwebend*`-Funktionen in `arbeitskopie.ts`. Vier Routen in `host.ts`: `uebernehmen`, `verwerfen`, `veroeffentlichen`, `zustand`.
- **KI-Seitenleiste.** `betreiber-config.ts` (`/etc/regoro/ki.json`, **betreiberweit**), `integrationen.ts` (`.regoro/integrationen.json`, **pro Site**, Schlüssel des Kunden), `kontingent.ts`, `arbeitskopie.ts`, `validate.ts`, `relay.ts`, `recherche.ts`, `sandbox.ts`, `agent.ts`, `agent-worker.ts`, `agent-tools.ts`, `verlauf.ts` (Gesprächsverläufe: Persistenz, Auswahl, Nachlesen, Aufräumen), `modell-info.ts` (Kontextfenster beim Anbieter erfragen). Der Worker ist **dasselbe Binary** mit dem versteckten Unterbefehl `agent-worker` — kein zweites Release-Artefakt, kein Node auf dem Kundenhost.
- `scripts/gen-notices.ts` + `THIRD-PARTY-NOTICES.txt` — Lizenzhinweise, **Rechtspflicht**: Ein `--compile`-Binary trägt keine einzige Lizenzdatei aus `node_modules`, alle Lizenzen im Baum verlangen aber die Weitergabe ihrer Copyright-Hinweise. Eingebunden wie das Overlay (`with { type: "file" }`), ausgegeben von `regoro licenses`. Die Paketliste kommt aus **`bun.lock`**, nicht aus `node_modules`: 8 Plattform-Varianten von `@mariozechner/clipboard` sind hier nicht installiert, werden aber in anderen Release-Zielen ausgeliefert. Standardtexte für Pakete ohne eigene Lizenzdatei liegen in `scripts/spdx/`; fehlt dort eine benötigte Kennung, bricht der Generator ab, statt sie wegzulassen.
- `install.sh` — Installer (POSIX sh): lädt Binary + `SHA256SUMS` vom GitHub-Release, verifiziert, legt nach `~/.local/bin/regoro`. Bricht ohne `git` oder ohne Prüfsumme ab.
- `.github/workflows/release.yml` — baut auf Tag `v*` vier Binaries (`bun build --compile --target=bun-{linux,darwin}-{x64,arm64}`), erzeugt `SHA256SUMS`, hängt beides ans Release. **Asset-Namen müssen zu `install.sh` passen** (`regoro-<os>-<arch>`).
- `examples/site/` — Beispiel-Website, die die Tests als Fixture nutzen (`REAL_SITE`).

`VERSION` in `cli.ts` ist gegen `package.json` per Test festgenagelt — beide zusammen bumpen.
`cli.ts` führt `main()` nur unter `import.meta.main` aus; ohne den Guard startet ein Import die CLI.

## Nicht-verhandelbare Invarianten (bei Änderungen erhalten!)
1. **Zwei Schreibwege, zwei Regeln.** Seit der KI-Seitenleiste erzeugt nicht mehr nur der Server Markup. Die alte Invariante gilt unverändert für den Text-Editor; für den Agenten tritt eine zweite daneben. Keine der beiden ersetzt die andere.
   - **1a — Text-Editor (unverändert):** Der Client schickt **nie Markup**, nur Befehle (Text, Offsets, Format-Flags). Der Server erzeugt **jedes** `<strong>/<em>/<u>/<a>/<span style=color>/<br>`. Deshalb kein HTML-Sanitizer nötig — validiert werden ausschließlich **`href`** (`isValidHref`) und **Farbe** (`isValidColor`/`normalizeColor`). Führe keine client-gelieferten HTML-Strings ein.
   - **1b — KI-Editor:** Der Agent **erzeugt** Markup, schreibt es aber nie in die ausgelieferte Website. Er schreibt in eine Arbeitskopie **außerhalb** des Site-Ordners; der Server übernimmt daraus nur Dateien, die `validateAgentOutput()` bestanden haben. Der Prüfschritt urteilt nie darüber, ob eine Änderung *gut* ist — nur über das, was kein denkbarer Kundenwunsch je erfordern würde.
     - **Der Lauf endet bei `<siteDir>/.regoro/schwebend/`, nicht in der Website.** Bis dahin ist alles wie zuvor — Symlink-Suche, Fremdänderungs-Abbruch, Punkt-Pfade raus, Löschung als Abbruchgrund, `lstat` + `pathInsideSite` auf beiden Seiten, Validierung je Datei, `ersteKollision` unmittelbar vor dem Schreiben. Nur das Ziel ist ein anderes. Erst `POST /edit/uebernehmen` trägt das Ergebnis in den Entwurf und committet dort. Der Grund steht im Plan: Der erste Moment, in dem der Kunde das Ergebnis sah, war vorher der, in dem es schon öffentlich war.
     - **Der Agent schreibt auch nach `schwebend/` NICHT selbst.** Die Sandbox hat genau einen beschreibbaren Pfad, und das bleibt die Wegwerf-Kopie unter `runtimeWurzel()`; der Elternprozess trägt das geprüfte Ergebnis herüber. Derselbe Weg wie beim Gesprächsverlauf und aus demselben Grund (Invariante 11). Wer den Agenten direkt in den Kundenordner schreiben lässt, hebt die Sandbox-Zusicherung auf, ohne dass ein Test rot wird.
     - **Kopiert wird aus dem ENTWURF, nicht aus dem Site-Ordner.** Der Agent arbeitet auf dem Stand, den der Kunde gerade bearbeitet. Gegen die veröffentlichte Website zu vergleichen hieße, gespeicherte, aber noch nicht veröffentlichte Kundenarbeit als „vom Agenten geändert" zu lesen und sie beim Übernehmen zu überschreiben. Das `.git` des Entwurfs überspringt `siteDateien()` als Punkt-Segment — der Agent sieht nie ein Repo, was sauberer ist als vorher.
     - **Validiert wird ZWEIMAL, und das ist kein Versehen.** Einmal am Laufende (gegen den Entwurf von damals; eine Ablehnung lässt den Lauf scheitern, es entsteht gar keine Ablage) und einmal beim Übernehmen (gegen den Entwurf von jetzt). Zwischen beiden können Tage liegen — eine offene Änderung soll Neustarts überleben. `validateAgentOutput` urteilt gegen den **Vorzustand** („was schon vorher dastand, bleibt gültig"), und der ist ein anderer, sobald sich am Entwurf etwas geändert hat. Die Prüfung, die zählt, ist die unmittelbar vor dem Schreiben; die erste erspart nur eine Ablage, die ohnehin niemand übernehmen könnte.
     - **Der Boden unter der Ablage wird mitgeschrieben.** `legeSchwebendAn` hält in `<schwebendDir>/.stand.json` fest, welchen Byte-Hash jede berührte Datei im Entwurf hatte (`null` = gab es nicht). Beim Übernehmen wird dagegen verglichen → `409 fremd-geaendert`. Ohne diese Aufzeichnung könnte die Zusicherung gar nicht anschlagen, und eine Zusicherung, die nicht anschlagen kann, beweist durch ihr Ausbleiben nichts. Der Zettel trägt ein Punkt-Präfix, damit ihn jeder vorhandene Walker übergeht — sonst zählte er als berührte Datei und landete beim Übernehmen in der Website des Kunden.
     - **Abgelegt werden BYTES, nicht ein dekodierter String.** Vorher las die Übernahme `readFileSync(quelle, "utf8")` und schrieb denselben String zurück. Für HTML und CSS folgenlos, für eine `.webp` oder `.woff2` nicht: Jedes ungültige Byte wird beim Dekodieren zu U+FFFD und beim Schreiben zu drei anderen Bytes. Der Validator bekommt weiterhin Text, abgelegt wird das Original. Dieselbe Falle, die `byteHashDatei` schon einmal nötig gemacht hat.
     - **Gebaut wird daneben, dann umbenannt.** `legeSchwebendAn` schreibt in einen Punkt-Ordner und benennt erst am Ende um. Ein Absturz mitten im Schreiben hinterließe sonst eine HALB abgelegte Änderung, die von außen wie eine vollständige aussieht — der Kunde übernähme drei von fünf Dateien, genau der Zustand, gegen den „alles oder nichts" seit jeher antritt. Die verbleibende Lücke (Absturz zwischen Räumen und Umbenennen) kostet die Ablage und ist damit die harmlose Richtung.
     - **Inline-`<script>` ist erlaubt und wird am INHALT gemessen — wie eine eigene `.js`-Datei.** Ein pauschales Verbot stand hier einmal und kaufte nichts: Eine eigene `.js` ist erlaubt, `<script src>` ebenso, und die erzeugte CSP führt `script-src 'self' 'unsafe-inline'` mit Absicht (die Fabrik baut ihren Seitenkopf damit). Beide Formen laufen mit denselben Rechten auf derselben Herkunft; das Verbot erzwang eine Datei mehr, sonst nichts. Schlimmer: Die Asymmetrie lief falsch herum — eine neue `.js` wurde inhaltlich geprüft, ein Inline-Block gar nicht erst angesehen, sondern abgelehnt. Und es kostete real: Für eine **neue** Datei ist jeder Inline-Block zwangsläufig neu, der Agent konnte den Fabrik-Seitenkopf also nie vollständig kopieren — gemessen an einer angelegten Produktseite: Menüknopf tot, `--kanon-kopfhoehe` beim CSS-Rückfall, auf dem Handy ein zerdrückter Kopf, auf **jeder** neu angelegten Seite. Geprüft wird jetzt in beiden Formen dasselbe (Navigationsregel, Service-Worker), und zwar gegen den Vorzustand: Was schon vorher dastand, bleibt gültig. Wer das Verbot wieder einführt, muss zuerst erklären, was es gegenüber der erlaubten `.js`-Datei verhindert.
2. **Auth ausschließlich datei-basiert, Nachweis per Einmalcode:** `<siteDir>/.regoro/auth.json` (`v:2`, Listen `nummern`/`emails` + per-Site HMAC-Secret). **Kein Passwort, kein argon2id** — mit ihm verschwand ein Überlastungshebel (jeder Versuch kostete ~64 MB, ungebremst von außen auslösbar). **Fail-closed:** kein/ungültiges/veraltetes File, oder leere Kennungsliste → alle `/edit*` inkl. Anmeldung → 404. Eine `v:1`-Datei wird **abgelehnt**, nicht migriert (`pruefeAuthDatei` → `"veraltet"`).
   - **Die Anmeldung ist zweistufig:** Kennung (Telefonnummer *oder* E-Mail) → Einmalcode. Unterschieden wird an der **Anwesenheit** des Feldes `code`, nicht an seinem Inhalt und nicht an einer serverseitigen Sitzung. Auf „nicht leer" zurückgebaut hieße ein versehentlicher Leer-Klick im Code-Formular „neuen Code anfordern": eine zweite, kostenpflichtige Nachricht, und der Code aus der ersten wäre tot, weil `merkeCode` ihn ersetzt. Ein leeres Feld verbraucht auch keinen der fünf Versuche — es ist ein Vertipper, kein Rateversuch. Die Kennung reist im Formular mit; wer sie fälscht, hat trotzdem keinen gültigen Code.
   - **Dieselbe Antwort für hinterlegt und nicht hinterlegt** — in Inhalt, Statuscode **und Laufzeit**. Sonst verrät die Anmeldeseite, welche Nummern es gibt. Ebenso dürfen „Code falsch", „abgelaufen" und „Kennung unbekannt" nicht unterscheidbar sein. Tests: `login-code.test.ts`.
     - **Der Versand wird bewusst NICHT abgewartet** (`void versand.sendeCode(…).catch(…)`). Gemessen: mit `await` dauerte die Antwort 152 ms für eine hinterlegte und 0,2 ms für eine unbekannte Kennung — für jede beliebige Nummer nachprüfbar, ob sie zu dieser Website gehört. Ohne `await` bleibt ein Unterschied von ~1 µs. Nicht auf `await` zurückbauen.
     - **Ein Versandfehler geht ins Log, nie an den Browser.** Nur eine hinterlegte Kennung kann einen Versandfehler auslösen — ein 502 wäre ein rauschfreies Orakel. Der Kunde sieht auf der Code-Seite „Neuen Code anfordern".
     - **Die Frage „ist dieser Kanal eingerichtet?" steht VOR der Hinterlegt-Prüfung** und hängt nur vom gewählten Reiter ab (→ 503 für alle). Stünde sie danach, wäre der Zustand direkt nach `regoro init` — versand.json fehlt noch — ein offenes Orakel für jede Website.
   - **Codes und Bremszähler leben nur im Arbeitsspeicher** (`codes.ts`, `bremse.ts`) und gehen **niemals ins Log** — auch nicht gekürzt, auch nicht im Fehlerfall. Vergleich über `safeEqual`, nie `===`.
     - **Deshalb geht aus einer Anbieter-Antwort nur der HTTP-Status in die Fehlermeldung, nie der Rumpf** (`versand.ts` → `ruf()`). `nurCode()` **prüft** den seven.io-Statuscode gegen `^\d{3}$`, statt ihn zu kürzen — Kürzen genügte nicht: Ein Rumpf `Code: 424242` ergab `Code424242` und trug den Einmalcode vollständig ins Log (gemessen). Ein dreistelliger Wert kann keinen sechsstelligen Code enthalten. Der Rumpf gehört dem Anbieter, und eine 4xx-Antwort spiegelt gern die Anfrage zurück — die enthält Code und Empfänger. Ein Filter über Steuerzeichen genügt dafür **nicht**: der verhindert gefälschte Log-Zeilen, nicht den Code im Log. Wer die volle Antwort braucht, findet sie im Dashboard des Anbieters.
   - **Die Bremse greift VOR dem Versand** und verbucht in einem Zug mit dem Fragen. Getrennt gäbe es einen Pfad, auf dem das Verbuchen ausbleibt (Versand scheitert) — genau den würde jemand suchen, um kostenlos auszulösen. Sie zählt **auch unbekannte Kennungen**, sonst wäre sie selbst ein Orakel. Der Kostendeckel ist `MAX_PRO_KENNUNG` (nur hinterlegte Kennungen kosten Geld); `MAX_PRO_SITE` ist eine Flut-Sperre und deshalb hoch angesetzt — eine Handvoll erfundener Nummern darf nicht die Anmeldung aller Kunden einer Website sperren. Echte Flut-Abwehr gehört in den Reverse-Proxy — das gilt für **beide** Zähler.
     - **Je Kennung wächst eine Wartezeit, es gibt keinen festen Deckel** (`STUFEN_MS = [1 min, 1 min, 5 min]`, letzte Stufe gilt dauerhaft weiter). Der frühere feste Deckel („drei pro Stunde, dann zu") ist an einem echten Fall gescheitert: Drei Anfragen sind mit einem Tippfehler, einem zweiten Gerät oder einer Mail im Spam-Ordner verbraucht, und danach steht der **zahlende Kunde** 54 Minuten vor verschlossener Tür. Ein Kostendeckel, der den Kunden häufiger aussperrt als den Angreifer, ist am falschen Ende scharf. Preis der Änderung, bewusst bezahlt: höchstens ~12 Nachrichten je Stunde statt 3 — die harte Kostengrenze ist das Guthaben beim Versanddienst, nicht diese Datei.
     - **Eine erfolgreiche Anmeldung setzt die Treppe zurück** (`entsperreKennung`, gerufen direkt nach `pruefeCode(...) === "ok"`). Die Bremse begrenzt Anfragen von jemandem, der sich **nicht** anmelden kann; wer gerade einen gültigen Code vorgelegt hat, ist genau der, für den sie nie gedacht war — er darf am zweiten Gerät nicht warten. Kein Orakel: Auslösen kann es nur, wer einen gültigen Code besitzt, und beobachten nur derselbe. Die **Flut-Sperre der Website bleibt dabei unberührt** — sie zählt über alle Kennungen, und dass ein einzelner Kunde sich anmeldet, sagt darüber nichts. Beide Gegenproben stehen als Tests.
     - **Ein gezielter Lockout bleibt möglich, wird aber billiger:** Wer die Geschäftsnummer kennt (sie steht im Impressum derselben Website), hält die Codes dieses Kunden auf Abstand. Zwei Entschärfungen, beide durch Tests festgehalten: Der **zweite Kontaktweg hat einen eigenen Zähler** und bleibt offen, und die Codes des Angreifers landen **beim Kunden** und funktionieren dort. Deshalb bei jedem Kunden nach Möglichkeit Nummer **und** Adresse hinterlegen.
   - **`createAuthFile` überschreibt kommentarlos** (Kennungen **und** Secret) — deshalb guardet `cmdInit` dagegen und verlangt `--force`. Zum Pflegen der Kennungen gibt es `schreibeKennungen`/`regoro kennung`; das rührt das Secret **nicht** an, damit eine hinzugefügte Nummer keine laufende Sitzung beendet.
   - **`init`-Reihenfolge nicht umstellen:** `ensureGitignore` → `ensureRepo` → `createAuthFile`. Der Baseline-Commit entsteht, wenn `auth.json` noch **nicht existiert** — das Secret kann gar nicht hineingeraten. Und ein fehlschlagendes `git` hinterlässt keine nutzlose Auth-Datei, die der „bereits initialisiert"-Guard dann blockieren würde. Tests: `cli.test.ts` → „git schlägt fehl".
   - **Cookie-Name nie hartkodieren** — `cookieName()` benutzen. In Prod ist er `__Host-regoro_edit`; das Präfix verbietet dem Browser `Domain=`-Cookies gleichen Namens, sonst könnte bei Subdomain-Betrieb (`kunde.site.example.de`) eine Geschwister-Subdomain die Session aller anderen verdecken. Ohne `Secure` (EDITOR_INSECURE_COOKIE=1) fällt das Präfix weg, sonst verwirft der Browser das Cookie.
   - **`readCookieTokens` liest ALLE gleichnamigen Cookies**, nicht den ersten. `isAuthed` prüft jeden gegen `checkCookie`. Nicht auf „erster Treffer" zurückbauen — das ist die zweite Verteidigungslinie gegen Cookie-Tossing.
   - **Sitzungsdauer 30 Tage.** Der Normalfall soll „gar keine Nachricht" sein. Der Ausgleich: Wer sofort aussperren will, erneuert das Secret (`init --force`).
   - **Die Anmeldeseite kommt ohne JavaScript aus** — sie ist die einzige Route ohne Auth-Wall. Die Reiter sind Links (`?weg=sms|email`), kein Skript. Nicht auf JS umbauen.
3. **Nur die Website ausliefern, nichts sonst.** Zwei Schranken, beide nötig:
   - **Dotfile-Block** in `host.ts` (public-GET-Zweig + `serveAssetAus`, also auch die Vorschau-Auslieferung) → jeder Pfad mit `.`-Segment → 404. `.regoro/` ist zudem gitignored — **niemals committen**.
     - **Diese Zeile trägt seit dem Umbau deutlich mehr.** In `.regoro/` liegen jetzt nicht nur Sitzungsgeheimnis und Kontaktwege, sondern das **gesamte Entwurfs-Repo** und die schwebende Änderung — also jede unveröffentlichte Fassung der Kundenwebsite samt Historie. Fiele der Block weg, wäre nicht ein Geheimnis offen, sondern alles, was der Kunde je geschrieben und ausdrücklich noch nicht veröffentlicht hat. Aus demselben Grund filtert `siteDateien()` Punkt-Segmente und das Veröffentlichen kopiert und löscht sie nie.
   - **Extension-Allowlist** `ASSET_TYPES` (wohnt in `sites.ts`, `host.ts` re-exportiert sie nur — der Umzug ist dort kommentiert) → alles ohne bekannte Endung → 404. Ein Site-Ordner enthält real auch Build-Artefakte (`design.json`, `images.json` mit internen Serverpfaden), Backups, Notizen. Nimm **nie** `.json`/`.yaml`/`.md` in `ASSET_TYPES` auf; `.svg` bleibt draußen (script-fähig).
   - **Der Reverse-Proxy muss dieselbe Allowlist führen.** In `Caddyfile.example` liefert Caddy die statische Site direkt aus, der Bun-Host ist dafür nicht im Pfad — ein blankes `file_server` unterläuft `ASSET_TYPES` komplett (war so, gefixt). Ändert sich `ASSET_TYPES`, ändere das Caddyfile mit. Tests dazu in `security.test.ts` („404, obwohl die Datei existiert").
4. **Routing:** Präzedenz Alt-Repo-Riegel → `/edit/login` → `/edit-assets/*` → API-Routen (`save/upload/versions/restore/version`, `uebernehmen/verwerfen/veroeffentlichen/zustand`, `/edit-vorschau/*`) → View-Routen (`/edit`, `/<page>.html/edit`) → public static. View unauth → **302 Login** (`?return=`, streng validiert gegen Open-Redirect). API unauth → **404**.
   - **Eine Route steht an ZWEI Stellen in `host.ts` — und die erste ist die Auth-Wand.** `isApiRoute` entscheidet, ob eine Anfrage überhaupt in den Zweig hinter dem Cookie-Test kommt; die Zuordnung `path === … → handler` steht darunter. Wer nur die zweite ergänzt, baut eine Route, die **auch angemeldet 404 gibt** — die Anfrage fällt durch bis zum statischen Ausliefern. Genau so lag `/edit/agent/verlaeufe` einen Commit lang tot da.
   - **Und der Test, der das hätte finden müssen, war grün.** `agent-routes.test.ts` prüfte „unangemeldet → 404" — das stimmte, aber aus dem falschen Grund: Eine Route, die es gar nicht gibt, antwortet ebenso. Deshalb steht dort jetzt `ERREICHBAR` neben `ROUTEN`: dieselbe Liste, einmal angemeldet gefahren, mit dem Statuscode, den sie liefern **muss**. Eine Abwesenheits-Prüfung ohne diese Gegenprobe misst nichts. Wer eine Route ergänzt, ergänzt beide Listen.
   - **Der Proxy-Matcher muss `isEditorPath()` spiegeln.** `path /edit*` reicht **nicht**: es verfehlt die Suffix-Route `/<page>.html/edit` (der Editor war in Prod für jede Unterseite 404) und fängt zugleich öffentliche Seiten wie `/edit-preise.html` ein. `/edit-vorschau/*` gehört ebenfalls hinein — fehlt es, liefert Caddy die Vorschau-Assets aus dem Site-Ordner aus, und der Kunde begutachtet wieder neues HTML über altem CSS, diesmal ohne dass am Bun-Prozess etwas falsch wäre. Gilt für beide Vorlagen **und** `caddyBlock()` in `service.ts` — gemeinsam ändern.
   - **Die Fehlerform ist überall `{"fehler":"<kennung>","grund":"<deutscher Satz>"}`** — beides, nicht eins von beiden. `fehler` ist für die Maschine, `grund` für den Kunden. Vorher standen zwei Formen nebeneinander (`{error:…}` bei den alten Routen, `{ok:false,grund:…}` bei den Agenten-Routen), und der Browser musste raten. Der teuerste Fall war der `fileHash`-Konflikt: Er trug gar keine Kennung und wäre vom neuen „schwebende Änderung" nur am **Fehlen** eines Feldes zu unterscheiden gewesen — eine Prüfung auf Abwesenheit, und die misst hier erfahrungsgemäß nichts. Er heißt jetzt `konflikt`. Die Agenten-Routen behalten `ok:false` **und** `grund` und bekommen `fehler` nur dazu; bei `422 validierung` geht der **deutsche Satz aus `validate.ts`** unverändert hinaus, keine Kennung — der Validator schreibt bereits Klartext, und eine Kennung müsste rückübersetzt werden und veraltete bei jedem neuen Prüffall.
5. **Symlink-sicheres Schreiben:** `pathInsideSite()` (realpath-Containment, fail-closed) vor jedem Write. Nicht entfernen. Die Stellen sind `handleSave`, `handleUpload` (beide gegen `entwurfDir` statt wie früher gegen `siteDir` — dorthin schreibt der Editor jetzt), `uebernehmen`/`uebernimmSchwebend` in `agent.ts` (auf **beiden** Seiten, Quelle und Ziel) und das Veröffentlichen. `handleRestore` steht bewusst nicht mehr in der Liste: Es schreibt nicht selbst, sondern lässt git den Arbeitsbaum setzen.
6. **Range-Format-Ops werden beim Speichern aus dem Live-DOM abgeleitet** (`collectRangeOpsFromDom` in overlay.client.js) — additive Formatierung über `.__regoro-range-fmt`-Spans, Entfernung über `.__regoro-range-unfmt`-Marker. Grund: robust gegen zwischenzeitliche Textedits. Nicht auf fixe gespeicherte Offsets zurückbauen.
7. **Ephemer:** `data-edit-idx`/`data-edit-img-idx`/`data-edit-del-idx`/`data-edit-br-idx` werden nur in der `/edit`-Response injiziert, **nie auf Platte**. Roh-HTML ist die einzige Quelle, bei jedem `/edit`-Load neu abgeleitet.
8. **Optimistic Locking und Versionen — beides gilt für die GANZE Website.** `fileHash` → Mismatch = `409 {"fehler":"konflikt"}`. Versionen = Git im **Entwurfs-Repo** (`repoRoot === entwurfDir`); `stelleEntwurfBereit` legt den Baseline-Commit auf dem fertig deployten Stand an.
   - **Wiederherstellen gilt für die ganze Website, nicht je Seite** (`restoreVersion(repoRoot, commit)`, der Seitenpfad ist entfallen). Die Historie wächst dabei nur nach vorn: Der alte Stand wird ein **neuer Commit obendrauf**, nichts wird umgeschrieben.
     - **`checkout` kann das nicht, auch nicht über den ganzen Baum.** Gemessen an einem Wegwerf-Repo (v1: `index.html`; v2: `index.html` geändert + `zusatz.js` neu): `git checkout <v1> -- index.html` lässt `zusatz.js` stehen, `git checkout <v1> -- .` ebenso. Nur `git read-tree` gleicht den Index gegen einen Zielbaum ab und entfernt, was dort nicht vorkommt; leer gewordene Ordner nimmt es mit. Wer „Versionen pro Website" mit `checkout` baut, hat das Loch weiterhin, nur weniger sichtbar — ein Lauf, der Dateien anlegt, ließe sich nie als Ganzes zurücknehmen.
     - **`--reset -u`, nicht `-um`.** `read-tree -um` bricht ab, sobald der **Arbeitsbaum vom Index abweicht**: rc=128, `Entry 'index.html' not uptodate. Cannot merge.` Eine einzige nicht committete Datei machte das Wiederherstellen damit dauerhaft unmöglich — das Sicherheitsnetz wäre tot, genau wenn man es braucht. `--reset -u` verwirft lokale Änderungen und tut sonst dasselbe. Das ist hier richtig: „zurück auf Version X" ist eine ausdrückliche Ansage des Kunden, und jeder gespeicherte Stand ist ohnehin ein Commit.
     - **`clean -fd -e '.*'` daneben — und das `-e` ist tragend, nicht kosmetisch.** `read-tree` fasst **unversionierte** Dateien in keiner Variante an (gemessen). Ohne den `clean` überlebte eine unversionierte Datei die Wiederherstellung und ginge beim nächsten Veröffentlichen mit auf die Website — dasselbe Loch, nur eine Ebene versetzt. Und ohne `-e '.*'` löscht derselbe Befehl `.regoro/auth.json`: nachgemessen, die Datei ist danach weg — Sitzungsgeheimnis, Entwurfs-Repo und schwebende Änderung in einem Zug. Der Filter hält jedes Punkt-Segment heraus, auch legitimen Website-Inhalt wie `.well-known/`. Nie zu `-fdx` erweitern.
     - **Committet wird der INDEX, nicht eine Pfadliste.** `commitEdit` taugt dafür nicht: Sie kehrt bei leerer Pfadliste **still** zurück (mit Absicht — sonst committete ein Randfall den ganzen Index). Darauf gebaut, entstünde beim Wiederherstellen **nie eine Version**, der Vorgang hinterließe keine Spur in der Historie. Deshalb `commitAlles()`. Die No-op-Toleranz bleibt: Wiederherstellen auf den Stand, auf dem man schon steht, meldet rc=1 mit „nichts zu committen, Arbeitsverzeichnis unverändert" und erzeugt keine Leer-Version.
     - **Zwei getrennte Fallen, keine Kette.** Der leere `commitEdit` und der Abbruch von `-um` sehen verwandt aus, greifen aber nicht ineinander: Gemessen blockiert **Index ≠ HEAD** allein `read-tree -um` nicht (rc=0); blockierend ist ausschließlich **Arbeitsbaum ≠ Index**. Wer beides zu einer Ursache verschmilzt, sucht den zweiten Fehler an der falschen Stelle.
     - `--end-of-options` verträgt `read-tree` (anders als `checkout`, wo es den rev/path-Split bricht) — das commit-Argument kann dort nie als Flag wirken.
   - **Ein Service Worker hängt nicht an seiner Datei — deshalb hilft Zurücknehmen gegen ihn nicht.** Die Registrierung liegt im Browserprofil des Besuchers, und dorthin reicht kein Befehl, den dieses Repo kennt: weder Wiederherstellen noch Veröffentlichen noch Löschen.
     Zwei getrennte Messungen. (1) Entfernt der Editor die Datei? Ja — durch die echte Kette gefahren (echter Server, Attrappen-Worker, echte Sandbox, echtes git): Lauf legt eine Seite an, `uebernehmen` committet in den Entwurf, `veroeffentlichen` stellt sie öffentlich (anonym 200), `restore` auf die Baseline nimmt sie aus dem Entwurf, das nächste `veroeffentlichen` meldet `{"geschrieben":0,"geloescht":1}` — anonym **404**, Datei physisch weg, der Rest der Website unberührt. Vor dem Veröffentlichen ist sie anonym 404: Ein Service Worker, der nur im Entwurf steht, erreicht keinen Besucher. (2) Überlebt die Registrierung, dass ihre Datei 404 wird? Ja — gemessen an einem **eigenständigen** Wegwerf-Server, auf dem sich das 404-Werden takten ließ (Chromium 151.0.7922.108, snap); regoro kam darin nicht vor, weil die Frage am Browser hängt. Über drei Neuladevorgänge, einen erzwungenen `registration.update()` (wirft `TypeError`, räumt nicht auf) und echte Prozess-Neustarts mit dauerhaftem Profil blieb die Registrierung bestehen; `sw.js` wurde dabei **siebenmal** abgerufen und war siebenmal 404.
     **Die Trennung der beiden Messungen ist die Pointe:** Die Browser-Eigenschaft gilt **unabhängig von diesem Repo** — deshalb kann diese Begründung nicht wieder veralten, und wer sie nachprüfen will, braucht regoro dafür nicht.
     **Es gibt kein Zeitfenster, das man abwarten könnte.** „Wie lange liefert der Worker noch aus" hat keine Zahl als Antwort, sondern eine Bedingung: Die Registrierung endet, wenn der Besucher seine Browserdaten löscht oder eine Seite derselben Herkunft `unregister()` ruft. Beides kann der Editor nicht auslösen — auch das korrekt löschende `veroeffentliche()` nicht.
     Deshalb lehnt der Validator jede Berührung von `navigator.serviceWorker` ab, nicht erst das `register`. Wer künftig etwas zulassen will, das sich selbst am Leben hält (Service Worker, `registerProtocolHandler`, persistente Storage-Registrierungen), muss zuerst **diese Eigenschaft** ändern — nicht die Regel lockern.
     - **Die Messung konnte ein Verschwinden zeigen** — sonst bewiese ihr Ausbleiben nichts: Positivkontrolle im selben Lauf (Phasen mit `sw.js`=200 zeigen die Entstellung, sonst meldet das Prüfskript sich selbst als ungültig), und getrennt `unregister()` → anzahl=0, nächster Aufruf zeigt wieder die Fassung aus dem Netz.
     - **Nicht gemessen:** echte Wanduhr-Zeit (mehrere Prozessneustarts und sieben Update-Abrufe, aber keine Tage) und andere Browser. Ob Chromium nach Wochen doch aufräumt, ist offen — es ließ sich nicht nachstellen, und darauf lässt sich keine Regel bauen.
     - **Die frühere Begründung war „`restoreVersion` löscht nie, also bleibt `sw.js` mit 200 erreichbar" — sie ist tot**, seit das Wiederherstellen über den ganzen Baum geht. Der alte Nachweis hatte zu früh aufgehört: Er zeigte, dass die Datei liegen bleibt, und schloss daraus auf das Überleben des Workers; geprüft war nur die erste Hälfte. Dass die Regel trotzdem richtig war, war Glück. Eine **zweite** tote Prämisse steckte daneben: dass Änderungen sofort live gehen und die Versionsliste das einzige Netz sei — darauf ruhte ausdrücklich die Entscheidung *gegen* einen Freigabeknopf, und genau den gibt es jetzt. Die alte Fassung zeigte auf ein **Werkzeug**, das wir kontrollieren, die neue auf eine **Eigenschaft**, die wir nicht kontrollieren; deshalb kann diese beim nächsten Umbau nicht wieder veralten.

   - **Ein Commit ist eine gespeicherte Änderung des Kunden, keine Seite.** Deshalb ignoriert `GET /edit/versions` sein `?page=` und liefert die Historie der ganzen Website; `unveroeffentlichtAnzahl` in `GET /edit/zustand` zählt aus demselben Grund **Commits**, nicht Dateien. Eine Liste „Versionen dieser Seite" neben einem Knopf, der den ganzen Baum zurücksetzt, wäre aktiv irreführend: Der Kunde wählte einen Eintrag, weil seine Seite darin steht, und bekäme alles andere gleich mit zurückgedreht. `GET /edit/version/<commit>?page=` bleibt seitenbezogen — `showVersion` liest genau einen Pfad.
   - **JEDER Schreibweg in den Entwurf endet mit einem Commit** — `save`, `upload`, `uebernehmen`. Das ist keine Kosmetik: Das Baum-Kommando bricht bei schmutzigem Arbeitsbaum hart ab, eine einzige nicht committete Datei machte das Wiederherstellen damit **dauerhaft** unmöglich — das Sicherheitsnetz tot, genau dann, wenn man es braucht. Wer einen vierten Schreibweg ergänzt, committet ihn.
   - **Immer nur EINE Bearbeitung offen** (Plan §3). Solange eine KI-Änderung schwebt, antworten `save`, `upload`, `restore` und `agent` mit `409 {"fehler":"schwebende-aenderung"}`. Nicht nur die beiden, die der Plan namentlich nennt: `upload` ist ein Speichern in Verkleidung, und `restore` verschöbe den Boden unter der schwebenden Änderung — sie scheiterte hinterher an `fremd-geaendert`, und der Kunde hätte einen bezahlten Lauf verloren, ohne je eine Wahl gehabt zu haben. Der Riegel für den Agenten sitzt in `starteLauf`, nicht nur in der Route, damit ein zweiter Eingangskanal ihn von selbst mitbekommt.
9. **Das ENTWURFS-Repo ist die einzige Quelle der Kundenänderungen — der Site-Ordner ist ein Abzug.** Die Historie liegt vollständig in `<siteDir>/.regoro/entwurf/`; was ausgeliefert wird, entsteht daraus durch `veroeffentliche()`. Zurücksetzen heißt: im Entwurf auf einen alten Stand gehen und ausrollen — ein Mechanismus statt zweier.
   - **Vor der Initialisierung gehört die Website der Fabrik, danach dem Entwurfs-Repo.** Es gibt zu jedem Zeitpunkt genau einen Schreiber. Reihenfolge bei der Umstellung: **erst deployen, dann initialisieren** — der Baseline-Commit entsteht auf dem fertigen Stand, es gibt nichts zusammenzuführen. Technisch festgehalten: `stelleEntwurfBereit` schreibt `veroeffentlicht.json` gleich mit, die Eigentums-Übergabe passiert also bei der Einrichtung und nicht erst beim ersten Veröffentlichen. Deshalb ist direkt nach `init` `unveroeffentlichteCommits === 0` und der Abzug **ist** der Baseline-Commit.
   - **Was `disable` entfernt, entscheidet sich am WERT, nicht am Ort.** Genau diese Verwechslung war die Ursache des teuersten Fehlers dieses Umbaus: Hier stand „`disable` ohne `--purge` entfernt nur `.regoro/`" — ein Satz über einen ORDNER, dessen Inhalt sich unter ihm verändert hat. Als dort nur `auth.json` lag, stimmte er; seit dort Entwurfs-Repo und schwebende Änderung liegen, hätte derselbe Befehl die gesamte Kundenarbeit gelöscht, während die Meldung „die Website läuft weiter" sagte. Die Regel lautet deshalb: **Was Zugang gewährt, verschwindet; was Kundenarbeit oder Abrechnung ist, bleibt.**
     - Ohne `--purge`: `auth.json` und `integrationen.json` weg. Fail-closed bleibt vollständig — ohne `auth.json` ist `/edit*` 404, und das ist der ganze Zweck von `disable`.
     - Stehen bleiben: `entwurf/` (Historie), `schwebend/` (bezahlte, noch nicht übernommene Arbeit), `veroeffentlicht.json` (ohne sie hebelte das Wiedereinschalten stillschweigend die Notbremse aus), `kontingent*.json`.
     - **Warum ausgerechnet die Abrechnung bleibt** — hergeleitet, nicht gemessen: Das Staging-Kontingent ist **einmalig**, es kennt keinen Monatsreset (`Kontingentart`, C9). Verschwände `kontingent-staging.json` beim Abschalten, wäre `disable` + `init` genau der Reset, den es nicht geben soll — „einmalig" wäre dann nur so dauerhaft wie die Disziplin des Betreibers. Der Pflichtparameter aus C9 verhindert den vergessenen Vorgabewert; diese Zeile verhindert dieselbe Wirkung durch eine andere Tür. Dass nur der Betreiber `disable` ausführen kann, ist kein Gegenargument: Es geht nicht um einen Angreifer, sondern darum, dass ein Mechanismus hält, ohne dass jemand aufpassen muss.
     - Erst `--purge` räumt `entwurf/` weg, und nur wenn der Guard es erlaubt.
   - **Der `--purge`-Guard muss das ENTWURFS-Repo zählen** (`countCommits(entwurfPfad(siteDir))`), nicht den Site-Ordner. `null` bleibt Abbruch, `> 1` bleibt Abbruch.
     - **Die lehrreiche Hälfte: eine Zusicherung kann sterben, ohne dass jemand sie berührt.** `countCommits` beginnt mit `if (!existsSync(join(repoRoot, ".git"))) return 0` — völlig korrekt, **solange** „kein Repo" ehrlich „nichts zu verlieren" hieß. Der Umbau hat diese Gleichung aufgelöst, ohne die Funktion anzufassen: `<siteDir>/.git` gibt es nie mehr, die Antwort ist immer 0, und der Guard ließ `--purge` durch. Gemessen an einer Site mit vier Commits im Entwurf: `countCommits(siteDir) = 0`, `countCommits(entwurfDir) = 4`. Der Kommentar an der Funktion sprach dabei weiter von fail-closed. Wer eine Ablage verschiebt, muss jede Frage mitziehen, die auf sie zeigt.
   - **Die Prüfsummen in `veroeffentlicht.json` sind eine Notbremse, kein Sicherheitsnetz.** Sie verhindern keinen zweiten Schreiber und retten seine Arbeit nicht; sie sorgen dafür, dass wir sie nicht wortlos zerstören — dieselbe Idee wie das `fileHash`-Locking des Text-Editors, eine Ebene höher. Deshalb **fail-soft**: Fehlt die Datei oder ist sie kaputt, ist das Ergebnis `[]`. Fail-closed wäre hier falsch — eine fehlende Aufzeichnung ist der Normalzustand vor der ersten Veröffentlichung, und eine kaputte Datei blockierte das Veröffentlichen dauerhaft.
   - **Die Trennlinie ist nicht „Regelverstoß", sondern „würde Veröffentlichen fremde Arbeit zerstören".** Danach fällt jeder Fall von selbst: eine aufgezeichnete Datei mit anderem Inhalt ist **fremd** (wir überschrieben sie); eine Datei auf der Website, die wir nie geschrieben haben, ebenfalls — denn gelöscht wird über `geloescht = ziel \ quelle`, und eine nie veröffentlichte Fremddatei fiele genau darunter; eine aufgezeichnete Datei, die **fehlt**, ist **nicht fremd** — derselbe Regelverstoß, aber sie trägt keine fremde Arbeit, das nächste Veröffentlichen schreibt sie korrekt zurück. Wer die Grenze am Verstoß statt am Schaden zieht, blockiert das Veröffentlichen in Fällen, die sich selbst heilen.
   - **Zweiphasig: erst planen, dann ausführen.** Fremdprüfung, Schreib- und Löschliste und jeder Zielpfad werden fertig berechnet, bevor die erste Datei angefasst wird. Ein Abbruch mitten im Kopieren hinterließe eine halb veröffentlichte Website — einzelne Seiten neu, andere alt, Verweise dazwischen ins Leere.
   - **Punkt-Segmente werden nie kopiert und nie gelöscht.** Fiele der Filter, nähme die erste Veröffentlichung `.regoro/` mit: Im Entwurfs-Arbeitsbaum steht kein `.regoro`, und die Löschliste erfasst alles, was auf der Website steht und im Entwurf fehlt. Deshalb prüft `sicherOhnePunkt()` unmittelbar vor Schreiben und Löschen noch einmal und bricht ab, statt zu löschen — redundant mit Absicht.
   - **Leere Ordner mit `rmdirSync` abräumen, nicht mit `rmSync`.** `rmSync(dir, { recursive: false })` wirft auf einem Verzeichnis (EISDIR); das `catch` daneben schluckte es, und der leer gewordene Ordner blieb wortlos stehen — im Nachweis aufgefallen, im Code unsichtbar. `recursive: true` ist die falsche Abhilfe: Der Ordner ist leer oder er bleibt, rekursiv könnte er einen Punkt-Eintrag mitnehmen.
   - **Ein `<siteDir>/.git` OHNE Entwurfs-Repo schaltet den Editor ab** (`istNichtMigriert`, geprüft in `route()` vor allem anderen): 404 für alles unter `/edit`, die Website läuft weiter. Danebenzuschreiben wäre der teure Ausgang — es entstünden zwei Historien, und das erste Veröffentlichen rollte einen leeren Entwurf über die echte Website. Es gibt keine Migration, weil es keine Bestandsseiten gibt. Die Meldung geht **einmal je Site-Ordner** ins Log, nicht je Anfrage: Sie steht im 404-Pfad, und ein Browser, der `/edit` alle zwei Sekunden neu lädt, schriebe sonst das Journal voll — genau dort, wo der Betreiber die eine erklärende Zeile suchen muss.
10. **Kundentrennung im Sammelbetrieb:** `HostCtx` entsteht pro Anfrage aus dem normalisierten `Host`-Header. Die Trennung zwischen Kunden ruht auf drei unabhängigen Stützen: der Host-Auflösung (`sites.ts`, fail-closed), dem site-eigenen HMAC-Secret in `auth.json` (ein fremdes Cookie ist nicht verifizierbar) und `resolvePage`/`pathInsideSite` (ein fremder Pfad ist nicht auflösbar). Keine der drei darf entfallen — die erste ist Zuordnung, die zweite Identität, die dritte Containment. Tests: `multisite.test.ts`.
   - **Stütze 2 hält nur, solange die Geheimnisse verschieden sind.** Wird ein Site-Ordner samt `.regoro/` kopiert, teilen sich zwei Kunden Secret **und** Passwort-Hash — dann gilt nicht nur das Cookie des einen beim anderen, sondern dasselbe Passwort öffnet beide Logins (ein an den Host gebundenes Cookie schlösse nur die erste Hälfte). `erstelleSecretWache()` in `sites.ts` erkennt das und liefert für **beide** Seiten `auth === null` (Editor 404, Website läuft weiter). Zugeordnet wird über den **Ordner** (realpath), nicht den Hostnamen — zwei Namen per Symlink auf dasselbe Verzeichnis sind ein legitimer Alias. Nicht entfernen.
   - **Die Wache leitet aus dem IST-Zustand ab, nicht aus der Geschichte** — sie sieht das Sammelverzeichnis reihum durch (höchstens einmal pro `SECRET_SCAN_TTL_MS`), statt gesehene Geheimnisse zu sammeln. Nicht auf ein Gedächtnis zurückbauen: das hätte zwei gemessene Löcher — zwei gleichzeitig angelegte Duplikate fielen nie auf, wenn nur eines je eine Editor-Anfrage bekommt, und eine behobene Kollision heilte erst beim Neustart, was den unbeteiligten Kunden aussperrt. Die Deckelung per TTL ist Notwehr: `/edit/login` ist unauthentifiziert, eine Durchsicht pro Anfrage wäre ein Verstärker (eine Anfrage → N Dateizugriffe).
   - **`normalizeHost` ist zugleich der Traversal-Schutz** — der Host-Header wird zum Pfadsegment. Nicht lockern; `resolveSite` prüft zusätzlich auf *direktes* Kind des Sammelverzeichnisses.
   - **Einen Kill-Switch braucht der Sammelbetrieb nicht:** `buildCtx` liest `auth.json` pro Anfrage, `regoro disable` wirkt dadurch von selbst sofort. Im Einzelbetrieb bleibt der Guard in `server.ts`.
   - **Im Caddy-Block des Sammelbetriebs steht der Host-Header im `root`-Pfad** (`root * <sitesRoot>/{host}`). Deshalb sitzt `@badhost` (Zeichensatz `CADDY_HOST_RE`) davor: gemessen liefert `Host: ..` sonst Dateien **eine Ebene über** dem Sammelverzeichnis mit 200 aus. Go weist `/` im Host selbst ab (400), reine Punkte nicht.
   - **Caddys `{host}` ist der Host-Header wörtlich** — es normalisiert nichts. Deshalb spiegelt `CADDY_HOST_RE` die `HOST_RE`-Grammatik aus `sites.ts` Zeichen für Zeichen (nur Kleinbuchstaben, echte Label), per Test aneinander gebunden. Eine laxere Fassung ließ `a..b` und `KUNDE.DE` durch: Caddy lieferte den gleichnamigen Ordner öffentlich aus, während der Editor denselben Host ablehnte — ein Publikationsweg, den kein Editor-Werkzeug zeigt. Caddy darf **strenger** sein als der Editor, nie laxer. **Site-Ordner immer kleingeschrieben und ohne `www.` anlegen.**
   - **`on_demand_tls` ohne `ask` ist grob fahrlässig** — jeder fremde Hostname könnte Zertifikatsanfragen auslösen. `TLS_ASK_PATH` (`server.ts`) antwortet nur für existierende Ordner; der Pfad ist per Test an `caddyGlobalBlock()` gebunden.
11. **Der Agentenprozess hält keine Zugangsschlüssel und besitzt kein Werkzeug für beliebige Netzverbindungen.** Suche, Seitenabruf und Modellaufruf laufen über den **Elternprozess**; der Schlüssel wird erst in der Loopback-Weiterleitung (`relay.ts`) angehängt. Der Grund ist die Kombination, die 2025 reihenweise ausgenutzt wurde (Cursor CVE-2025-54135, Copilot CVE-2025-53773, GitLab Duo): fremder Text als Eingabe, ein Geheimnis in der Umgebung, ein offener Ausgang. Zwei davon nehmen wir dem Agenten weg.
    - **Was der Worker über die Außenwelt wissen muss, erfragt der ELTERNPROZESS und reicht es durch.** Der Worker läuft mit `allowModelNetwork: false` und registriert sein Modell selbst — er kann pi gar nicht beim Anbieter nachfragen lassen. Die Versuchung ist dann, die Angaben fest einzutragen, und genau das war passiert: `contextWindow: 128_000` stand im Code, während OpenRouter für dasselbe Modell 1.048.576 meldet (`top_provider.context_length`; alle 424 Modelle führen den Wert). Folge, gerechnet: pi verdichtete ab 111.616 Token statt ab 1.032.192 — mitten in großen Aufträgen (größter gemessener Lauf: 207.371 Token), jede Verdichtung ein zusätzlicher abrechenbarer Modellaufruf, und `keepRecentTokens` (20.000) warf dabei fast das ganze Gespräch weg. `modell-info.ts` fragt jetzt im Elternprozess einmal je Modell nach (gecacht, 4 s Zeitlimit, **fail-soft** auf den alten Wert) und gibt das Ergebnis als `REGORO_CONTEXT_WINDOW` und `REGORO_MAX_TOKENS` mit. Die Sandbox bleibt unberührt. **Wer hier eine weitere Anbieterangabe braucht, geht denselben Weg — nicht die Zahl in den Worker schreiben.**
      - **`top_provider.context_length` schlägt `context_length`.** Das erste ist, was der tatsächlich bedienende Anbieter kann, das zweite das theoretische Maximum des Modells; bei `glm-5.3-flash` sind das 1.048.576 gegen 1.310.720. Die größere Zahl anzunehmen hieße, Anfragen zu bauen, die abgelehnt werden.
      - **Der Ausgabedeckel (`maxTokens`) hing an derselben Krankheit** und war 16.384 — auf der Leitung nachgemessen geht er als `max_completion_tokens` wirklich an den Anbieter. Zu knapp an zwei Stellen zugleich: Werkzeug-Argumente sind Ausgabe (`write_file` übergibt die ganze Datei, 16.384 Token sind grob 55–60 KB HTML), und pi stutzt das Denk-Budget auf denselben Deckel zurecht. Jetzt `min(150.000, was der Anbieter meldet)`, ohne dessen Angabe gedeckelt durch das Kontextfenster — die einzige Schranke, die sich aus dem Modell selbst ergibt. Gemessen: OpenRouter nimmt einen zu großen Wert stillschweigend an und klemmt intern; ein strenger OpenAI-kompatibler Server lehnt ab. Auf keines von beiden verlassen wir uns.
      - **Die Abfrage ist eine Stellschraube, keine Voraussetzung.** Kein Anbieter, kein `/models`, kaputtes JSON, Zeitlimit — alles fällt auf den Vorgabewert zurück und der Lauf startet. Auch der Rückfall wird gemerkt, sonst wartete jeder Lauf eines Anbieters ohne `/models` erneut ins Zeitlimit.
    - **Der Worker startet aus einer Allowlist-Umgebung**, nicht aus `process.env` minus ein paar Namen. Auf der Entwicklungsmaschine sind `HTTP_PROXY`/`HTTPS_PROXY` gesetzt; erbte der Worker sie, gelänge ein Modellaufruf **am Relay vorbei** — und ein kaputtes Relay fiele niemandem auf.
    - **Drei Grenzen, keine ersetzt die andere:** Betriebssystem (`bwrap` je Lauf + systemd `ProtectSystem=strict`), Werkzeuge (eigene, kein `bash`, kein generisches Netzwerkzeug), Browser (CSP im Caddy-Block). Die dritte liegt außerhalb dessen, was der Agent schreiben kann — deshalb steht sie im Proxy und nicht im HTML.
    - **`regoro ki` ist betreiberweit** (`/etc/regoro/ki.json`), wie `versand.json`. `regoro disable` schaltet **einen** Kunden ab und lässt sie unangetastet — sonst nähme das Abschalten eines Kunden allen anderen die KI. Die Kundenschlüssel liegen getrennt davon pro Site in `.regoro/integrationen.json`.
    - **Zwei Eigenheiten von `bwrap` unter `--ro-bind / /`**, beide in `sandbox.ts` gelöst und beide dieselbe Familie wie die `ProtectHome`-Falle:
      - **Ein Deckel auf einen Pfad, den es auf dem Host nicht gibt, bricht den Lauf ab** — gemessen: `bwrap: Can't mkdir /etc/gibt-es-nicht: Read-only file system`. Im nur lesbaren Wurzeldateisystem lässt sich kein Einhängepunkt anlegen. Deshalb wirft `sandboxArgv` nicht existierende Ziele vorher raus. **Die Kehrseite: Ein fehlendes Verzeichnis wird stillschweigend NICHT zugedeckt.** Für `/etc/regoro` ist das folgenlos, solange es leer ist — die Deckelliste entsteht bei jedem Lauf neu, ein später angelegter Schlüssel ist ab dem nächsten Lauf verdeckt. Wer den Filter entfernt, bekommt statt dessen abgebrochene Läufe auf jedem Host ohne `/etc/regoro`.
      - **`--tmpfs /home` verdeckt auch das Binary**, wenn es dort liegt (`bwrap: execvp: No such file or directory`). Deshalb holt `sandboxArgv` die Programmdatei mit `--ro-bind` hinter dem Deckel zurück — nur die Datei, nicht ihr Verzeichnis. In Produktion liegt das Binary in `/usr/local/bin` und der Fall tritt nie ein; er trifft ausschließlich die Entwicklungsmaschine und verführt dort zur bequemen Abhilfe, den `/home`-Deckel wegzulassen.
    - **Zwei systemd-Schalter brechen `bwrap` lautlos** und fehlen in `systemdUnit()` mit Absicht: `RestrictNamespaces=yes` (sperrt alle Namespace-Typen; bwrap braucht `user`, `mnt`, `pid`) und `SystemCallFilter=@system-service` (schließt `@mount` aus — nachgezählt mit `systemd-analyze syscall-filter`). Nicht „als Hardening nachtragen".
    - **`LoadCredential=` braucht `SetCredential=ki:{}` daneben.** Gemessen auf systemd 255: Fehlt `/etc/regoro/ki.json`, bricht `LoadCredential` den Start mit `status=243` ab — der Dienst läuft nicht mehr. Mit dem Fallback startet er, `loadKiConfig` gibt für `{}` null zurück, die KI ist aus. Fail-closed statt tot.
    - **`WorkingDirectory=` darf NICHT gequotet werden** (`sdPfad()`, nicht `sdQuote()`). systemd nimmt dort den Rest der Zeile wörtlich, die Anführungszeichen würden Teil des Pfades: „path is not absolute", der Dienst startet nicht. Für `ExecStart=` und `ReadWritePaths=` sind sie umgekehrt zwingend. Beides gemessen.
12. **Drei Zustände, drei Orte — und der Editor liefert nie den falschen aus.**

    | Zustand | Ort | wer sieht ihn |
    |---|---|---|
    | **Entwurf** (KI) | `<siteDir>/.regoro/schwebend/` — nur die berührten Dateien | Kunde, überlebt Neustarts |
    | **Entwurf** (manuell) | Browser-DOM | Kunde, stirbt mit dem Tab |
    | **Gespeichert** | `<siteDir>/.regoro/entwurf/` — git-Repo, Arbeitsbaum = ganze Website | Kunde |
    | **Veröffentlicht** | `<siteDir>/` — reiner Abzug | die Besucher |

    - **Der Kernbeweis, an dem dieses ganze Vorhaben hängt, ist EINE Messung:** `/edit` liefert den Entwurfsstand, dieselbe Seite öffentlich abgerufen den veröffentlichten — und nach einem Speichern ist die ausgelieferte Datei **byteidentisch** mit vorher. Ohne diese drei Aussagen zusammen ist der Umbau nicht belegt, sondern nur geschrieben: Zwei davon allein ließen sich auch durch einen Editor erfüllen, der weiterhin live schreibt. Nachgewiesen an 16 Abschnitten mit rund 90 Zusicherungen gegen `buildCtx` + `handleEditorRequest`, gefahren auf einer echten Kopie von `examples/site`.
      **Kein Statuscode zeigt das an** — beide Sichten antworten 200. Wer es prüfen will, muss Entwurf und Site-Ordner absichtlich auseinanderlaufen lassen und danach fragen, welche Markierung wo herauskommt.
      **Und wenn eine einzige Zahl hier stehen soll, dann diese:** Ein KI-Lauf legt eine Seite an → anonym **404**. `uebernehmen` committet sie in den Entwurf → anonym **weiterhin 404**. Erst `veroeffentlichen` → anonym **200**. Die mittlere Zeile ist der ganze Umbau: **übernommen, aber nicht veröffentlicht, und der Besucher sieht es nicht.** Vor dem Umbau war dieselbe Anfrage an dieser Stelle 200. Rückwärts ebenso gemessen: `restore` + `veroeffentlichen` meldet `geloescht:1`, die Datei ist physisch weg, und `/index.html`, `/styles.css`, `/assets/hero.png` antworten unverändert 200.
    - **Die Wurzel wird je ANFRAGEKLASSE gewählt, nicht je Pfad.** `host.ts` führt dafür drei Auflösungen statt einer: `seiteFuerAnsicht` (schwebend über Entwurf — was der Kunde begutachtet), `seiteImEntwurf` (wohin geschrieben wird), `seiteOeffentlich` (was ausgeliefert wird). Sie zu einer zusammenzufassen und die Wurzel aus dem Pfad zu raten wäre der sichere Weg, sie eines Tages zu verwechseln — und eine Verwechslung heißt entweder „der Kunde prüft den falschen Stand" oder „ein Entwurf steht öffentlich".
    - **Die öffentliche Auflösung führt KEINE Whitelist**, und das ist keine Lockerung. Die Whitelist entstand aus `discoverPages` → `readdirSync(withFileTypes).isFile()`; „steht auf der Liste" hieß immer schon „ist eine reguläre top-level-Datei mit erlaubtem Namen", und genau das prüft `lstatSync().isFile()` direkt. Die Liste des ENTWURFS hierfür zu nehmen wäre falsch herum: Eine veröffentlichte Seite, die im Entwurf gelöscht wurde, verschwände für die Besucher, obwohl die Datei ausgeliefert dasteht. Gegenüber dem Vorzustand ist es sogar strenger — wo `existsSync` stand, folgte die Prüfung einem Symlink, `lstat` tut das nicht.
    - **Statische Dateien der Editor-Ansicht kommen über `{basis}/edit-vorschau/<pfad>`**, auth-bewacht, `no-store`. Der Grund ist gemessen und war die teuerste Falle des Umbaus: `renderEditView` macht Asset-URLs root-absolut, diese GETs treffen den **öffentlichen** Zweig, und in Produktion liefert Caddy sie sogar direkt von Platte — der Bun-Prozess ist dafür gar nicht im Pfad. Die „Vorschau" zeigte damit Entwurfs-HTML über **veröffentlichtem** CSS. Ändert der Agent das Stylesheet (was er routinemäßig tut), prüft der Kunde das Falsche, und „erst ansehen, dann übernehmen" ist genau dort gebrochen, wo es gebraucht wird.
      - **Warum kein Cookie-Schalter am öffentlichen Zweig** („angemeldete Anfragen bekommen den Entwurf"), was näher liegt: Er verlangte, dass Caddy **jede** Anfrage mit Editor-Cookie an Bun weiterreicht — der öffentliche Auslieferweg bekäme eine Auth-Entscheidung, die er heute nicht hat. Und er legte zwei verschiedene Inhalte auf **dieselbe URL**; jeder geteilte Cache lieferte dann irgendeinen von beiden, der Preis wäre `Vary: Cookie` überall. Mit eigenem Präfix ist es eine andere URL, ein anderer Cache-Eintrag, und der öffentliche Pfad bleibt unberührt.
      - Angenehm nebenbei: Relative URLs **innerhalb** eines Stylesheets (`url(images/bg.png)`) lösen von selbst mit auf den Präfix auf — der Browser rechnet sie gegen die URL des Stylesheets, und die trägt ihn bereits. Dafür braucht es keine Sonderbehandlung, und wer eine einbaut, hat den Mechanismus missverstanden.
    - **Der Bild-Upload liefert ZWEI Adressen für eine Datei, und das ist keine Redundanz.** Ins HTML geschrieben wird der veröffentlichte Pfad `/assets/<datei>` — ein `edit-vorschau`-Präfix im gespeicherten Markup überlebte das Veröffentlichen und zeigte den Besuchern auf eine auth-bewachte Adresse. An den Browser zurück geht dagegen `{basis}/edit-vorschau/assets/<datei>`, denn nach dem Upload liegt die Datei im Entwurf und im ausgelieferten Ordner noch gar nicht. Mit nur einem Wert wäre nach jedem Bildtausch **genau dieses eine Bild** kaputt, während alle anderen der Seite funktionieren — die hat `rewriteAssetUrls` längst umgeschrieben. Diese Asymmetrie innerhalb einer Seite ist zugleich das Erkennungszeichen. Der Browser übernimmt `src` **unverändert** und stellt nichts davor: Die Konvention gehört dem Server, zwei Quellen dafür wären schlimmer als der Fehler, den sie beheben.
    - **Veröffentlichen ist ein eigener, ausdrücklicher Schritt.** Vorher veröffentlichte **auch der manuelle Editor sofort** — sein „Speichern" schrieb direkt in die ausgelieferte Datei. Der Unterschied zum KI-Editor war nie „mit Freigabe gegen ohne", sondern nur, dass der Kunde vorher hinsah. Jetzt schreiben beide an denselben Ort, und Veröffentlichen ist ein einziger Vorgang für alles, was seit dem letzten Mal zusammengekommen ist — auch für gemischt manuelle und KI-Änderungen über mehrere Tage.
    - **In Staging gibt es kein Veröffentlichen**, und `POST /edit/veroeffentlichen` sagt das mit `403 {"fehler":"staging"}`. Die Prüfung steht im Server und nicht nur in der Oberfläche: Ein Knopf, den das Overlay ausblendet, ist keine Zusicherung — ein `curl` käme sonst durch.
    - **`ctx.staging` fasst die Auth-Wand NICHT an** (Contract C12). Staging unterscheidet sich allein im **Aussteller** des Cookies, und der lebt im Staging-Handler in `server.ts`. Der Produktionsprozess enthält diesen Code nicht und kann ihn deshalb nicht erreichen — dieselbe Logik wie „das ohne Anmeldung gehört an den Prozess, nicht an den Kundenordner", eine Ebene tiefer: keine Fahne, die man falsch setzen kann, sondern Code, der dort nicht vorkommt. Wer hier ein `if (staging)` in die Auth-Entscheidung schreibt, macht aus einer Struktureigenschaft wieder einen Schalter.
13. **Die Leiste kommt aus EINEM Zustand — und jeder Pfad geht durch `u()`.** (Beitrag Frontend-Dev, gemessen.)
    - **Es ist höchstens EINE Bearbeitung offen**, die manuelle im Browser-DOM oder die schwebende der KI. „Speichern" und „Verwerfen" wirken auf die, die gerade offen ist — hinter „Speichern" steht bei einer schwebenden Änderung `POST /edit/uebernehmen`, sonst `POST /edit/save`. Ein Wort, eine Bedeutung, zwei Mechanismen. Zwei Knopfpaare nebeneinander wären zwei Werkzeuge für dieselbe Handlung, und der Kunde müsste raten, welches seines ist. `updateButtons()` ist die einzige Stelle, die die Leiste setzt: Knopf für Knopf an den Aufrufstellen zu schalten hieße, dass jeder neue Weg alle Knöpfe kennen muss — einer wird vergessen.
    - **`CFG.zustand` kommt vom Server mit, `ladeZustand()` führt ihn nach — FAIL-SOFT.** 404, kaputtes JSON, Zeitlimit: Der zuletzt bekannte Zustand bleibt stehen, die Leiste arbeitet weiter (Prüffall `zustand-fehlt`). **Nicht auf „ohne Zustand keine Leiste" zurückbauen**: „nichts offen" ist von den beiden möglichen Auskünften die gefährlichere, deshalb wird sie nie geraten.
    - **Die Zustandszeile ist NICHT `status`.** `status` sagt, was gerade geschah, und wird von jeder Aktion überschrieben; die Zustandszeile sagt, was gilt. Zusammengelegt verschwände „Offene KI-Änderung, 12 Tage alt" beim ersten Klick. **Das Alter ist der eigentliche Inhalt** — eine Änderung von vorhin und eine von vor zwölf Tagen sehen sonst gleich aus.
    - **„Veröffentlichen" fehlt in Staging ERSATZLOS** (`CFG.staging === true`), es ist nicht gesperrt. Ein grauer Knopf sagt „geht gerade nicht"; dort gibt es aber kein Ziel, und daran ändert kein Warten etwas. Aus demselben Grund schweigt die Zustandszeile dort über Unveröffentlichtes. („Speichern" ist umgekehrt nur hervorgehoben, wenn etwas offen ist — ein Knopf, der immer hervorsticht, trägt keine Auskunft.)
    - **Nichts davon hängt an `CFG.ki`.** Ohne Modellzugang fehlt genau der KI-Knopf; Veröffentlichen hängt am unveröffentlichten Stand, nicht am Modell. Der Prüffall `ohne-ki` prüft ausdrücklich, dass die **Leiste** entsteht. Dieselbe Kopplung ist serverseitig für die vier Kernrouten verboten (der `ctx.ki == null`-Riegel steht innerhalb des `/edit/agent`-Zweigs) — hier ist sie eine Ebene weiter vorn dieselbe Regel: Wird der Modellzugang abgeschaltet, während eine Änderung schwebt, muss der Kunde sie noch übernehmen oder wegwerfen können.
    - **`u(pfad)` stellt `CFG.basis` voran**, leer in Produktion, `/p/<slug>` in Staging. **Ein vergessener Pfad ist in Staging ein stummer 404** — der Editor sieht aus wie immer und tut nichts. Deshalb geht kein absoluter Pfad mehr hinaus, auch keiner, der heute nur in Produktion gebraucht wird.
      - **Falle, hineingelaufen:** In `ladeNachrichten` hieß eine lokale Variable `u` und verdeckte die Hilfsfunktion — der Gesprächsabruf wäre mit „u is not a function" gestorben. **Kein `u` als lokaler Name in dieser Datei.** `tsc` sieht das nicht (die Datei ist kein TypeScript), der Browser-Build auch nicht (er parst nur).
      - **Gegenprobe:** Der Prüffall `praefix` weist jeden `/edit…`-Pfad **ohne** Präfix mit 404 ab; nachgewiesen, dass er anschlägt — mit einem `u()`, das den Pfad unverändert durchreicht, wird er rot und die übrigen bleiben grün.
      - **Die Bild-`src` aus der Upload-Antwort wird UNVERÄNDERT übernommen.** Welcher Pfad die Entwurfs-Sicht ist, weiß der Server (Invariante 12). Schriebe der Browser den Präfix selbst davor, hätte dieselbe Konvention zwei Quellen — und die zweite veraltet.
    - **Das erste eigene Modal, und `confirm()` reicht dort nicht.** Elf Stellen der Datei benutzen native Dialoge; diese nicht. Jede Frage hier hat **zwei benannte Antworten**; ein `confirm()` kennt nur „OK" und „Abbrechen", eine der Handlungen hieße dann „Abbrechen", und welche, müsste man dem Fließtext entnehmen. Bei einer Frage, deren eine Antwort Arbeit wegwirft, ist das nicht zumutbar.
      - **Der Drei-Tage-Hinweis (C8) hat KEIN „Abbrechen".** Wer daran vorbeikäme, bekäme genau den Auftrag, den er nicht beurteilen konnte.
      - **Die drei Riegel beim Absenden stehen in dieser Reihenfolge:** ungespeicherte Handarbeit → offene KI-Änderung → Drei-Tage-Hinweis. Nicht tauschen: Der dritte kann den ganzen Entwurf zurücksetzen und nähme eine ungeklärte Handarbeit aus dem ersten stillschweigend mit.
      - **Der nachgereichte Auftrag wird beim LESEN gelöscht** (`holeAuftrag`), vor dem Senden. Er reist im `sessionStorage` über den Reload, den „Änderungen verwerfen" auslöst. Bricht danach etwas ab, liegt nichts mehr da, das beim nächsten Laden ein zweites Mal losliefe — ein Geisterauftrag kostet echtes Geld und wäre nicht erklärbar.
      - **Die Rückfrage vor dem Wiederherstellen spricht von der GANZEN WEBSITE**, und die Handlung steht auf dem Knopf („Ganze Website zurücksetzen"), nicht nur im Text darüber. Der Kunde steht auf EINER Seite und klickt in einer Liste, die neben dieser Seite aufgeht — „diese Version wiederherstellen" liest sich dort zwangsläufig als „diese Seite". Deshalb heißt die Liste auch „Versionen der Website". Keine Dateinamen im Warnsatz, mit Absicht: Sie bräuchten eine neue Route, und Wiederherstellen ist umkehrbar (der jetzige Stand bleibt als Version).

- **`tsc` vor `bun test`, immer.** `bun test` **führt TypeScript aus, ohne es zu prüfen** — ein Typfehler ist für die Suite unsichtbar. Genau deshalb konnte `src/cli.ts` über mehrere Commits unübersetzbar sein, während alle Tests grün meldeten (das fehlende `firecrawlKey` im Objektliteral). Umgekehrt sind Testfehler nach einem gescheiterten Typecheck fast immer Folgefehler und kosten nur Lesezeit.
- **Ein Nachweis, der nicht anschlagen kann, beweist durch sein Ausbleiben nichts.** An einem Tag dreimal dieselbe Fehlerklasse, jedes Mal an anderer Stelle und von jemand anderem gefunden:
  - `test.skipIf` wertet beim **Einsammeln** aus, vor jedem `beforeAll` — vier Binary-Tests waren dauerhaft übersprungen und meldeten **grün**.
  - Zwei `service.test.ts`-Zusicherungen nagelten die **kaputte** Form von `WorkingDirectory=` fest; deshalb erzeugte der dokumentierte Deploy-Weg nie eine startfähige Unit, und niemand sah es.
  - Die Prüfung „Agent-Routen geben 404 ohne `ki.json`" lief zuerst **unangemeldet** — dort geben sie ohnehin 404 (Invariante 4). Das erwartete Ergebnis kam aus dem falschen Grund.

  Zeichenketten-Prüfungen halten fest, was wir für richtig **halten**; ein Vergleich mit der eigenen Erwartung kann einen Irrtum in der Erwartung grundsätzlich nicht finden. **Wo ein Test eine Abwesenheit behauptet** („kein fatal error", „kein Proxy-Durchgriff", „keine Datei außerhalb"), gehört deshalb eine Gegenprobe daneben, die den Messapparat selbst prüft. Die drei, die dafür im Repo stehen: das absichtlich wieder eingebaute Quoting, das `systemd-analyze` als `fatal error` sehen **muss**; das Kind mit geerbter Umgebung, das durch den Attrappen-Proxy **durchkommen muss**, bevor gezeigt wird, dass der echte Lauf scheitert; und die Attrappe, die meldet, dass sie den Ausbruch **wirklich versucht** hat und an EROFS gescheitert ist — ohne sie wäre der wichtigste Test dieser Arbeit auch dann grün, wenn sie gar nichts täte.

  Und wo es geht: **das echte Werkzeug fragen**, statt die erzeugte Zeichenkette zu vergleichen — `systemd-analyze verify`, echtes `caddy` auf der Leitung, kompiliertes Binary ohne `bun` im PATH. Genau diese drei Prüfungen haben die drei teuersten Fehler gefunden.
- **Für die drei Zustände gibt es eine Falle, die kein Zeichenketten-Test findet: die WURZEL.** Ob `/edit` den Entwurf und `/` den veröffentlichten Stand liefert, steht in keinem Statuscode — beide antworten 200. Ein Test, der nur „200" prüft, ist deshalb wertlos. Was misst: Entwurf und Site-Ordner **absichtlich auseinanderlaufen lassen** (verschiedene Markierungen hineinschreiben) und dann prüfen, welche Markierung wo herauskommt. Dasselbe gilt für die Vorschau-Assets — dort mit der Gegenprobe daneben, dass die **öffentliche** Seite den Präfix nie trägt.
  - **Und dabei eine Seite nehmen, die überhaupt Assets hat.** Genau daran ist die erste Fassung dieser Messung gescheitert: Die Prüfseite war auf `<p>Markierung</p>` zusammengekürzt, es gab kein `<link>` und kein `<img>`, also wurde auch nichts umgeschrieben — der Fall meldete einen Fehler im Code, wo der Messapparat leer lief. `examples/site/index.html` trägt `styles.css` und zwei Bilder; auf ihr messen, nicht auf einem Kunstgebilde.
- **Was `bun test` über den Umbau NICHT sagt:** Ob nach einem Schreibweg der Entwurfs-Arbeitsbaum **sauber** ist. Ein vergessener Commit fällt erst auf, wenn Wochen später jemand wiederherstellen will und das Baum-Kommando abbricht. Die Prüfung ist billig und gehört neben jeden Schreibweg: `git -C <entwurfDir> status --porcelain` muss leer sein.
- **`disable`/`--purge` gegen eine Site mit echter Historie fahren, nicht gegen eine frische.** Die Guards zählen Commits; auf einer Site, die nur den Baseline-Commit hat, verhalten sich „geschützt" und „ungeschützt" gleich, und der Test wäre grün, ohne etwas zu messen. Anlegen: Site initialisieren, drei Fassungen in den Entwurf committen, dann erst prüfen.
- **Das Binary muss nach jeder Änderung an Asset-Laden/Pfaden echt geprüft werden**, `bun test` deckt nur den dev-Pfad ab. Minimal: Binary bauen, `PATH=/usr/bin:/bin` (kein bun), `regoro init` + `run` auf einer tmp-Kopie (Port über `PORT=…`, **`run` kennt kein `--port`**), dann `/edit-assets/overlay.js` → muss 200 liefern und **deutlich über 50 KB** sein, nicht 404. Bewusst eine Schwelle statt eines Punktwerts: Die Datei wächst mit jedem Ausbau (91 KB → 116 → 132 innerhalb eines Tages), und ein Punktwert wird bei jedem Wachstum zum falschen Alarm. Geprüft wird „ausgeliefert und nicht leer", nicht „exakt so groß". Dasselbe für die Lizenzdatei: `regoro licenses | wc -c` muss ~620.000 liefern, nicht 0. Das Binary ist ~90 MB.
- **Die erzeugte systemd-Unit gegen echtes systemd prüfen**, nicht nur per String-Vergleich — **und zwar aus dem KOMPILIERTEN BINARY**:
  ```bash
  bun build --compile src/cli.ts --outfile /tmp/regoro
  /tmp/regoro service <site> --systemd > /tmp/x.service && systemd-analyze verify /tmp/x.service
  ```
  Ein Textvergleich hat jahrelang eine Unit durchgewinkt, die wegen des gequoteten `WorkingDirectory=` gar nicht startete — deshalb gibt es diese Prüfung überhaupt.
  - **Der naheliegende Weg über `bun src/cli.ts service …` misst NICHTS, und er sagt es nicht.** `regoro service` verweigert unter `bun` den Dienst („braucht das kompilierte Binary"), die Umleitung erzeugt eine **leere Datei**, und `systemd-analyze verify` meldet darauf **rc=0** mit „Unit is masked". Ein grünes Ergebnis, das nie eine Direktive gesehen hat. Genau die Fehlerklasse, vor der der Absatz darüber warnt — diesmal in der Anleitung, die davor warnt, und ausgerechnet bei der Prüfung, die eingeführt wurde, weil ein Textvergleich sie nicht ersetzen konnte.
  - Gegenprobe, die den Messapparat selbst prüft: das Quoting absichtlich wieder einbauen — `systemd-analyze` **muss** dann „fatal error" melden. `systemd-run --user -p …` prüft einzelne Direktiven ohne root.
- **Der SSE-Strom hängt nicht an Caddy, sondern am ersten Byte.** Gemessen (caddy 2.11.4): Caddy gibt die Antwort-Header erst mit dem ersten Körper-Byte heraus — 4,00 s Verzögerung, wenn der Lauf 4 s schweigt, und `flush_interval -1` ändert daran **nichts**. Deshalb schickt der Editor beim Verbinden sofort einen SSE-Kommentar (`: verbunden`); damit sind es 0,002 s. Nicht entfernen, und die Verzögerung nicht im Proxy suchen.
- **install.sh ist ungetestet durch die Suite.** Prüfen gegen einen lokalen „Release": Binary + `sha256sum regoro-* > SHA256SUMS` in einen Ordner, `python3 -m http.server`, dann `HOME=/tmp/x REGORO_BASE_URL=http://localhost:PORT sh install.sh`. Auch die Abbruchpfade fahren (manipuliertes Binary → Prüfsummen-Fehler, fehlendes SHA256SUMS, fehlendes git). Zuletzt gefahren am 2026-09-04: alle vier Wege wie beschrieben, jeder Abbruch installiert nichts.
  - **Den „ohne git"-PATH als ALLES AUSSER git bauen, nicht als Liste des vermeintlich Nötigen.** Zwei Anläufe sind daran gescheitert: erst fehlte `mktemp`, dann `cp`, und beide Male brach der Lauf mit „not found" ab — was wie ein Fehler in `install.sh` aussah. Eine Auswahlliste behauptet Wissen über ein Skript, das sich ändert, und jede Lücke fällt dem Prüfling zur Last. Umgekehrt (`for f in /usr/bin/* /bin/*; do [ "${f##*/}" = git ] && continue; ln -sf …; done`) gibt es die Fehlerklasse nicht.
  - **Zwei Zusicherungen, die nicht anschlagen konnten** — beide hier hineingelaufen: Ein fester Port lieferte 404 aus dem Verzeichnis eines hängengebliebenen Servers eines früheren Laufs, wodurch **jeder** Fall nach einem Fehler in `install.sh` aussah (freien Port zur Laufzeit suchen und warten, bis er wirklich antwortet). Und `[ -n "$ver" ]` nach `regoro --version` ist auch für eine Fehlermeldung wahr — geprüft gehören Exit-Code **und** Form.
  - Zum Prüfling gehört eine Gegenprobe je Abbruchpfad (mit passender Summe / mit `SHA256SUMS` / mit `git` muss es durchkommen) und eine Prüfung des Messapparats selbst: In diesem PATH darf `git` wirklich nicht auffindbar sein und alles andere sehr wohl.
- **overlay.client.js ist von keiner Prüfung erfasst** — `tsc` sieht sie nicht an (kein TypeScript), und `bun build --target=browser` prüft nur, ob sie sich parsen lässt. Ob die Oberfläche das Richtige **anzeigt**, steht damit nirgends fest, und genau dort kamen zwei echte Fehler heraus (ein misslungener Lauf sah aus wie ein Erfolg; ein nachgereichter Lauf wäre nie angezeigt worden).
  - **Für die KI-Seitenleiste gibt es dafür `scripts/seitenleiste-pruefstand.ts`** (`bun scripts/seitenleiste-pruefstand.ts`, Port 8794). Er liefert die **echte** `overlay.client.js` mit erfundenen Ereignisfolgen aus — kein Modell, kein Kontingent, keine Sandbox, kein Netz, immer dasselbe Ergebnis — und druckt je Fall die Erwartung im Klartext plus einen fertigen headless-Aufruf. **Erst dort nachsehen, bevor jemand so etwas neu baut.** Bewusst ein Werkzeug und keine `*.test.ts`: Der Browser-Treiber liegt außerhalb des Repos, und ein Test, der überall außer auf einer Maschine übersprungen wird, sieht wie Abdeckung aus und ist keine.
  - **Der Prüfstand deckt inzwischen 31 Fälle ab** (vorher 15), davon fünf für die Gesprächsliste (`verlauf-nachlesen`, `-blaettern`, `-waehlen`, `-liste`, `-fehlt`). `scripts/pruefstand-treiber.py` fährt sie: liest die vom Prüfstand gedruckten Aufrufe samt Sollwert, führt sie aus, vergleicht — `python3 scripts/pruefstand-treiber.py [--neustart] <log> [Fallname …]`, Rückgabewert 0 bei grün.
    - **Der Treiber führt KEINE eigenen Sollwerte und keine eigenen Fälle.** Die Erwartung steht neben dem Fall, zu dem sie gehört. Eine zweite Liste wäre eine zweite Wahrheit, und bei Widerspruch wüsste niemand, welche recht hat.
    - **Drei Prüfungen messen die abgeschickte Anfrage scharf** (falsches `umfang` bei `/edit/verwerfen`, mitgeschicktes `?page=` bei `/edit/versions`, `pagePath` im Rumpf von `/edit/restore` → 400). Damit wird aus einem *Entfernen* etwas Prüfbares.
    - **Eine scharfe Prüfung nützt nichts, wenn kein Fall die Anfrage auslöst — genau das war passiert.** `wiederherstellen-loescht` hält beim Bestätigungsfenster an und schickt nie etwas ab; die `pagePath`-Prüfung lief nie. Nachgemessen: Mit wieder eingebautem `pagePath` blieb der Fall **grün**. Deshalb steht `wiederherstellen-ausfuehren` daneben, das durchklickt. **Wer eine scharfe Prüfung ergänzt, braucht einen Fall, der bis zur Anfrage durchläuft** — sonst hat er die Zusicherung erweitert und nicht die Abdeckung.
    - **Jeder Messlauf mit `--neustart` — Vorschrift, nicht Empfehlung.** `browse` hält EINEN langlebigen Browser; die Fälle öffnen laufend Ereignisströme auf dieselbe Herkunft. Gemessen: Nach etwa 120 Seitenaufrufen kommt `/edit-assets/overlay.js` nicht mehr durch — die Seite lädt mit 200, das Overlay läuft nie an, ab da meldet jede Prüfung eine Leiste, die es nicht gibt. **Ein Fehler im Aufbau der Leiste sieht genauso aus** (ebenfalls gemessen). Beides ist von außen nicht zu unterscheiden, deshalb steht hier bewusst **kein Erkennungszeichen**: Wer eines hätte, klärte damit früher oder später einen echten Einbruch weg. Aus einem frischen Browser heraus stellt sich die Frage gar nicht.
    - **„(no console errors)" beweist NICHT, dass kein Skriptfehler vorlag.** Gemessen: `browse console --errors` erfasst `console.error`, aber **keine unbehandelten Ausnahmen** — auch nicht solche lange nach dem Laden. Nachgestellt mit einem `buildBar()`, das eine noch nicht geschriebene Funktion anhängt: keine Leiste, und die Konsole schweigt. Für eine Datei, die `tsc` nicht ansieht, ist das die wichtigere Hälfte — ein ReferenceError im Aufbau ist genau der Fehler, den sonst niemand findet, und das naheliegende Werkzeug meldet ihn nicht. Prüfen lässt er sich nur am Verhalten: Gibt es `#__regoro-bar`?
  - **Der Fall `verlauf-fehlt` ist kein Randfall, sondern die Zusicherung**, dass ein Server ohne die Verlaufsrouten (404) die Leiste nicht lahmlegt. Die Gesprächsliste ist Komfort; sie darf nie im Auftragsweg stehen.
  - **Zwei Fallen im Prüfstand selbst, beide dort hineingelaufen** — er ist Code und irrt wie jeder andere: `Number(null)` ist **0**, nicht `NaN`, also lieferte die erste Seite eines Gesprächs (ohne `vor`) `slice(0,0)` und damit nichts; und „welche Fälle sind Nachlese" stand als `fallName === "…"` fest im Server statt am Fall. Beide Male sah es nach einem Fehler im Overlay aus, und beide Male war der Messapparat schuld. Wenn ein neuer Fall leer bleibt: erst den Prüfstand verdächtigen.
  - **Der Prüffall steckt im Cookie, nicht im Pfad.** Das Overlay ruft seine API unter festen absoluten Pfaden auf (`/edit/agent/...`); von einem Pfad-Präfix wäre dort nichts übrig, und jeder Fall zeigte dasselbe. Wer das übersieht, sucht den Fehler im Overlay statt im Prüfstand.
  - **Die Client-Datei bei JEDER Anfrage frisch von Platte lesen**, nie beim Start einmal. Sonst prüft man einen alten Stand und hält eine Änderung für wirkungslos. `host.ts` macht es aus demselben Grund so.
  - Für den **Text-Editor** (Selektion, Formatierung, Speichern) gibt es keinen Prüfstand: init+run auf einer temp-Kopie, im headless-Browser skripten, gespeichertes HTML prüfen.
- **Die Caddyfile-Vorlagen sind inzwischen weitgehend getestet.** `csp.test.ts` fährt ein echtes caddy hoch und prüft den ausgelieferten Header auf der Leitung — dass die CSP auf statischen Seiten steht und auf `/edit*` **nicht**, dass `design.json` und verschachtelte Dotfiles 404 geben, und dass eine freigeschaltete Browser-Herkunft wirklich im Header ankommt. Die `@allowed`- und die CSP-Zeile sind zusätzlich in Generator und **beiden** Vorlagen aneinander gepinnt.
  **Ungetestet bleibt der `on_demand_tls`-Pfad des Sammelbetriebs** — der braucht ACME und gehört in die Handprüfung. Zum Prüfen lokal nachbauen: Domain → `:PORT`, `auto_https off`, `reverse_proxy` → `respond`, dann per curl gegen einen Ordner mit Fremd-Datei (`design.json`, `dump.sql`) fahren — die müssen 404 geben, `/`, `*.html`, `*.css`, Unterordner-Assets weiterhin 200. **Auch verschachtelte Dotfiles testen** (`/assets/.private.html`, `/a/.hidden/notes.txt`): Caddys `path`-Matcher ist Glob, kein Segment-Matcher — `path /.*` deckt nur führende Punkte, daher `path_regexp (^|/)\.`.

## Fallstricke
- **Server nicht mit `repoRoot` = diesem Repo starten** für Dogfooding: der Save committet dann in genau dieses Repo. Immer auf einen **separaten Site-Ordner** zeigen (`cli.ts <site>` setzt `repoRoot = siteDir`).
- `EDITOR_INSECURE_COOKIE=1` (Cookie ohne `Secure`) wird **nicht** für `http://localhost` gebraucht — Browser akzeptieren dort `Secure`/`__Host-`-Cookies (in Chromium verifiziert), und **`curl` ebenfalls** (8.5 nachgemessen: Anmeldung über Loopback, danach `/edit` → 200 mit Jar, 302 ohne). Nötig nur bei HTTP unter fremdem Hostnamen/LAN-IP; dort verwirft der Browser das Cookie sonst **stumm** (Login-Schleife ohne Fehlermeldung). `insecureOriginWarning()` in `host.ts` warnt auf der Login-Seite vor. Nie in Prod.
  - **Der Schalter verfälscht die Prüfung, nicht nur die Sicherheit:** Ohne `Secure` fällt auch das **`__Host-`-Präfix** weg (`cookieName()`), denn der Browser verwürfe das Cookie sonst. Ein Durchlauf mit dem Schalter prüft also **nicht** den Produktions-Cookie — die Schutzwirkung des Präfixes gegen Cookie-Tossing bleibt ungetestet. Beim Ausprobieren deshalb weglassen, wo er nicht nötig ist.
  - **Eine leere Cookie-Datei ist meist ein Messfehler.** `curl` schreibt HttpOnly-Cookies mit `#HttpOnly_` am Zeilenanfang; ein `grep -v '^#'` filtert sie weg, und die Datei sieht leer aus, obwohl das Cookie darin steht. Genau daran ist eine Handprüfung schon einmal gescheitert und hat fälschlich `EDITOR_INSECURE_COOKIE=1` nachgezogen. Prüfen lässt es sich stattdessen am Verhalten: mit Jar 200 auf `/edit`, ohne Jar 302.
- Beim Ausprobieren `examples/site` nicht direkt bespielen (sonst nested `.git`/`.regoro` im Repo) — auf eine Kopie in `/tmp` arbeiten.
- Änderungen werden **nicht** automatisch mit dem alten `regoro-de/editor/` synchronisiert — dieses Repo pflegen.
